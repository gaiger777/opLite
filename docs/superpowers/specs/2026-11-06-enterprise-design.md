## 1. 목표와 범위

처음 분해에서 하위 프로젝트 10은 엔터프라이즈 기능이다: LDAP/SSO, 감사, 다중 클러스터 관리, 고급 DR(Proxmox의 realm·Datacenter Manager, vCenter의 이벤트·SSO·Linked Mode·Site Recovery). 지금 opLite는 로컬 사용자만 로그인하고, 누가 무엇을 했는지 남지 않으며, 클러스터 하나만 보고, 백업은 그 클러스터의 풀에만 있다.

### 견준 길

- **감사 로그 저장: 노드 로컬 파일(채택) vs Raft 리소스.** Raft에 두면 한 곳에 순서대로 모이지만, 로그인 실패마다 Raft에 쓰면 공격이 곧 쓰기 부하이고(계획 13이 같은 이유로 시도 제한을 노드마다 셈), 스냅샷이 모든 객체를 JSON 하나로 만들어 항목이 쌓이면 무거워지며, 정족수를 잃은 동안의 요청은 남지 않는다. 노드 로컬 파일은 이 셋이 없고, 읽을 때 노드 사이 RPC로 모은다. 꺼진 노드의 기록은 그 노드가 돌아와야 보인다(한계로 적음).
- **감사 지점: 라우터 미들웨어(채택) vs 핸들러마다 기록.** 미들웨어 하나가 모든 바꾸는 요청을 빠짐없이 적는다(새 API가 기록을 잊을 수 없음). 누가 했는지는 인증 추출기가 요청마다 둔 칸에 적어 미들웨어가 읽는다.
- **외부 사용자: 첫 로그인에 `User` 리소스를 만듦(채택) vs 세션에만 둠.** API 토큰, 세션 세대, 권한 확인이 모두 `User` id를 쓴다. 리소스를 만들면 이 경로를 그대로 쓰고, 관리자가 사용자 목록에서 외부 사용자를 보고 지울 수 있다. 역할은 로그인할 때마다 그룹·클레임으로 다시 정한다.
- **OIDC 구현: reqwest와 ring으로 직접(채택) vs `openidconnect` 크레이트.** 필요한 것은 discovery, 인가 코드 교환, JWKS로 RS256·ES256 서명 확인뿐이다. ring은 이미 의존성에 있다. `openidconnect`는 의존성이 많고 구조가 커서 얻는 것보다 다루는 비용이 크다.
- **LDAP: `ldap3` 크레이트(채택).** MIT/Apache, tokio 기반, StartTLS·LDAPS를 지원한다. 시험의 가짜 서버는 같은 프로젝트의 `lber`(BER 인코딩)로 짧게 만든다. 실제 OpenLDAP(slapd) 시험은 CI Linux에서만 기능 `ldap-it`로.
- **다중 클러스터: 각 클러스터에 원격을 등록하는 대등 구조(채택) vs 별도 관리 서버.** 따로 설치할 것이 없고 어느 클러스터에서도 다른 클러스터를 본다. 원격 쪽은 그 클러스터의 보통 API 토큰으로 권한을 정하므로 원격 클러스터에 새 개념이 필요 없다.
- **DR: 백업을 원격 클러스터로 복제(채택) vs 공유 NFS의 백업 받아들이기 vs 디스크 연속 복제.** 백업(계획 27·28)과 원격(계획 37)을 그대로 이어 쓰고, 원격 사본이 그 클러스터의 보통 백업이라 복원도 이미 있는 기능이다. 공유 NFS는 두 사이트가 같은 저장소를 보는 경우만 되고, 연속 복제는 스토리지 백엔드마다 다른 큰 일이다.

## 2. 감사 로그 (계획 34)

### 2.1 무엇을 적나

- 모든 `POST`·`PUT`·`PATCH`·`DELETE` API 요청(성공·실패 모두, 인증 실패 401·403 포함), `GET`의 VM 콘솔 열기(`/vms/{key}/console`), 로그인 성공·실패, 로그아웃.
- 적지 않는 것: 다른 `GET`, `/auth/whoami`, `/watch`, 웹 정적 파일, 노드 사이 RPC(사람의 요청이 아님).
- 항목(JSON 한 줄, `AuditEntry`):
  - `id`(UUID v7), `time`(유닉스 밀리초), `node`(노드 이름)
  - `user`(이름, 없으면 null — 인증 전·실패), `user_id`, `role`, `auth`(`session`·`token`·`none`)
  - `ip`(계획 13의 클라이언트 IP), `method`, `path`(쿼리 제외 — 쿼리에 비밀이 올 수 있음), `status`, `duration_ms`
  - `target`: 경로에서 읽은 `{ kind, key }`(예: `/vms/web-1/actions/start` → `vm`, `web-1`), 없으면 null
  - `action`: 경로 패턴 이름(예: `vm.start`, `user.create`, `auth.login`) — 라우트 표에서 정함
  - `detail`: 핸들러가 남긴 짧은 문자열(선택). 로그인은 시도한 사용자 이름과 영역, 구독 `PUT`은 키 id. 비밀(비밀번호·키·토큰)은 넣지 않는다.
- 요청 본문은 적지 않는다.

### 2.2 어떻게 적나

- `opl_api::router`에 미들웨어 `audit::layer`(axum `from_fn_with_state`). 요청 확장에 빈 칸 `AuditSlot`(`Arc<Mutex<..>>`)을 넣고 다음으로 넘긴 뒤, 응답 상태와 칸의 주체·`detail`로 항목을 만든다. 인증 추출기(`Principal`)는 확장에 칸이 있으면 주체와 인증 방식을 적는다. 로그인 핸들러는 성공하면 그 사용자를 칸에 적는다.
- 쓰기는 `AuditLog`(노드에 하나, `AppState`가 가짐)의 채널로 넘겨 별도 태스크가 파일에 덧붙인다(요청이 디스크를 기다리지 않음). 채널이 가득 차면(1만 개) 버리고 버린 수를 세어 다음 항목 앞에 `audit.dropped` 항목을 적는다.
- 파일: `{data_dir}/audit/audit.log`, 한 줄에 한 항목, 0600. 16 MiB를 넘으면 `audit.log.1`… 로 밀고 8개를 넘는 것은 지운다(opld 설정 `[audit] max_file_size`, `max_files`). 쓸 때마다 fsync하지 않고 1초마다 묶어서 한다.
- 같은 항목을 `tracing` 대상 `opl_audit`로도 내보낸다(info). systemd 아래에서는 journald로 가고, 관리자가 rsyslog 등으로 밖에 보낼 수 있다(README에 방법).
- opld 설정 `[audit] enabled`(기본 true). 끄면 파일도 tracing도 없다.

### 2.3 읽기

- `GET /api/v1/audit?since&until&user&node&action&limit`(admin). `since`·`until`은 RFC 3339 또는 유닉스 밀리초, 기본은 최근 24시간, `limit` 기본 200·최대 5000.
- 받은 노드가 노드 사이 RPC `ReadAudit`(필터와 한도)로 위트니스를 포함한 모든 멤버에게 묻고(자기는 직접), 시간 내림차순으로 합쳐 `limit`만큼 돌려준다. 각 노드는 회전한 파일까지 거꾸로 읽어 조건에 맞는 최신 `limit`개만 보낸다. 노드마다 5초 제한, 닿지 않은 노드는 응답 `unreachable: [이름]`에 넣는다. 응답 `{ entries, unreachable, truncated }`.
- 감사 로그 읽기 자체는 적지 않는다(GET).

### 2.4 oplctl과 웹

- `oplctl audit [--since 1h|<시각>] [--until] [--user] [--node] [--action] [--limit] [-o json]`: 표(시각, 노드, 사용자, IP, 동작, 대상, 상태).
- 웹 `/audit`(admin만 메뉴에 보임): 시간 범위(1시간·24시간·7일), 사용자·동작 거르기, 표, 닿지 않은 노드 경고, 행을 누르면 항목 JSON.

### 2.5 시험

- 단위: 경로 → `action`·`target` 표, 회전(크기·개수), 거꾸로 읽기와 거르기, 넘친 채널의 `audit.dropped`.
- API: 성공·403·401 요청이 주체와 함께 적힘, 로그인 실패에 사용자 이름이 `detail`에 있고 비밀번호는 어디에도 없음, 토큰 요청의 `auth: token`, GET은 적지 않음, `GET /audit` 권한과 거르기, 두 노드(`two_nodes.rs`)에서 합치기와 닿지 않는 노드.
- opld E2E: 실제 opld 둘에서 각 노드에 바꾸는 요청 → 한 노드의 `oplctl audit`이 둘을 모두 보임, 파일 권한 0600.
- 웹 Vitest: 표, 거르기, 경고, 권한에 따른 메뉴.

### 2.6 구현(계획 34)

- 타입(`opl_types::audit`): `AuditEntry`(§2.1의 필드), `AuditAuth{Session, Token, None}`(snake_case), `AuditTarget{kind, key}`, `AuditQuery{since, until, user, action, limit}`(`MAX_LIMIT` 5000, `matches`: 시각은 양 끝 포함, `user`는 정확히 같음), `AuditResponse{entries, unreachable, disabled, truncated}`. 설계와 다른 점:
  - `action`은 라우트 표의 이름(`vm.start`)이 아니라 `"<METHOD> <라우트 템플릿>"`(axum `MatchedPath`에서 `/api/v1`을 뗀 것, 예: `POST /vms/{key}/actions/{action}`, `POST /auth/login`)이다. 표를 따로 두지 않아 새 API가 저절로 이름을 가진다. VM 동작은 템플릿이 `/vms/{key}/actions/{action}` 하나라 `action`만으로는 가를 수 없으므로 `AuditQuery`의 `action` 거르기는 `action` **또는 `path`**의 부분 문자열이다.
  - `target`은 템플릿의 첫 조각(복수형 그대로 `vms`)과 템플릿의 첫 `{…}` 자리의 실제 경로 조각이다. 매개변수가 없는 템플릿은 None.
  - 넘친 기록은 `action: "audit.dropped"`, `detail: "<N> entries dropped"`, method·path·ip 빈 문자열, status 0.
  - (설계에 없음) 인증 없는 항목(`user` None — 인증 실패·로그인 실패·익명)은 IP마다 1분 창에 60개까지만 적는다. IP는 IPv4면 주소, IPv6면 /64 네트워크로 센다(계획 13 `limit::counted_ip`와 같은 규칙, IPv4-mapped는 IPv4). 넘친 것은 그 IP의 카운터로 세고, 창이 끝나면 쓰기 스레드의 1초 틱이 끝난 창을 훑어 `action: "audit.suppressed"`, `ip`(세는 단위 — IPv6는 `<네트워크>/64`), `detail: "<N> unauthenticated requests not recorded since <창 시작 RFC 3339>"`(`time`은 적는 시각), method·path 빈 문자열, status 0 항목을 적고 그 기록을 지운다(넘친 것이 없는 끝난 창도 지움). 그래서 넘친 수는 창이 끝나고 1초 안에 적힌다. 훑기 전에 그 IP가 다시 오면 그 항목 앞에, `shutdown` 때는 남은 것을 모두 적는다. 기록표는 IP 1만 개까지이고(끝난 창이 곧 지워지므로 1분 안에 서로 다른 IP 1만 개가 와야 닿음) 넘치면 가장 오래된 창을 버린다(그 카운터가 0이 아니면 그 `audit.suppressed`를 바로 적음). 가장 오래된 창과 끝난 창은 `(창 시작, 키)` `BTreeSet` 색인으로 찾아 표 전체를 훑지 않는다. 인증된 항목은 한도가 없다. 인증 없는 요청이 쏟아져도 파일이 회전으로 밀려 나가지 않게 하려는 것이다.
  - (설계에 없음) `path`·`target.key`·`detail`·`user`는 각각 512바이트까지만 적는다(UTF-8 글자 경계에서 자르고 끝에 `…`).
- 쓰기(`opl_api::audit`, `AuditConfig{dir, node, max_file_size, max_files}`·`AuditLog`): `disabled()`(아무것도 적지 않고 읽으면 빈 목록), `open(cfg)`(디렉터리 0700), `record`(동기 `try_send`, `node`는 설정의 노드 이름으로 덮음, 필드 자르기와 인증 없는 항목의 IP별 한도 — 시계는 `Instant`, 시험은 비공개 `record_at`), `read`(`spawn_blocking`), `shutdown`(채널에 남은 것과 남은 `audit.suppressed`를 쓰고 fsync, 5초 안에 끝나지 않으면 `warn!`하고 돌아감 — 종료 메시지는 막히는 `send` 대신 `try_send`와 10 ms async sleep을 마감까지 되풀이해 넘기므로 시간이 지나도 막힌 blocking 태스크가 남지 않는다), `is_enabled`. 쓰기 스레드가 끝난 뒤의 `record`는 처음 한 번 `warn!`하고 그 뒤는 버린 수로 센다. 설계와 다른 점: 쓰기는 tokio 태스크가 아니라 전용 스레드 `opl-audit`(std `sync_channel` 1만)다 — 파일 쓰기·fsync가 동기라서. `open`은 이미 있던 디렉터리도 0700으로 맞추고, `audit.log`를 `O_NOFOLLOW`로 열어(심볼릭 링크면 실패 — opld 시작 오류) 0600으로 맞추며(`libc`를 opl-api의 직접 의존으로), `max_files` 이상의 옛 `audit.log.N`(`max_files`를 줄인 경우)을 지운다. 파일 `audit.log`는 0600, 쓰기 전 크기 + 줄 길이가 한도를 넘으면(빈 파일이 아닐 때) 회전(`.{max_files-1}` 지우고 `.N` → `.N+1`, `audit.log` → `.1`), 쓴 것이 있으면 1초마다와 회전·종료 때 `sync_data`. 쓰기 실패는 `warn!`만 하고 다음 쓰기에서 파일을 다시 연다. tracing `opl_audit`(info, 메시지는 JSON) 줄은 파일에 쓸 때 낸다(버린 항목은 journald에도 없다). 읽기는 새 파일부터 통째로 읽어 줄을 거꾸로 훑고(망가진 줄 건너뜀), 파일의 가장 새 줄이 `since` 앞이면 멈추고 가장 오래된 줄이 `until` 뒤면 그 파일을 건너뛰며, `limit + 1`개까지 모은다(합칠 때 `truncated` 판단). 읽는 중에 회전하면 같은 항목이 두 파일에서 보일 수 있어 `id`로 중복을 없앤다.
- 기록 지점: `router()`가 `api()`에 `route_layer(from_fn_with_state(state, audit::layer))`를 붙인다(라우트가 맞은 요청만 — 맞는 라우트가 없는 404와 `/openapi.json`, opld의 제어 소켓·웹 정적 파일은 적지 않음). 메서드가 GET·HEAD·OPTIONS가 아니거나 템플릿이 `/vms/{key}/console`이면 요청 확장에 `AuditSlot`을 넣고 응답 뒤 항목을 만든다(`ip`는 `ClientIp`의 `to_canonical`, `path`는 쿼리 없는 `uri.path()`에서 `/api/v1`을 뗀 것). `Principal` 추출기가 `audit::note_auth`로 주체와 auth를 적는다 — `Authorization: Bearer `가 있으면 인증에 실패해도 늘 `token`. 핸들러는 추출기 `AuditNote`(실패 없음, 미들웨어 없으면 아무 일 안 함)의 `.detail(s)`·`.principal(p, auth)`로 남긴다: 로그인은 이름을 확인하기 전에 `username=<이름>`(이름 형식이 아니면 `username=<invalid>`)을 적어 401·429에도 있고 성공하면 그 사용자와 `session`, 로그아웃은 세션을 지우기 전에 그 사용자, 구독 `PUT`은 성공하면 `id=<키 id>`. 설계와 다른 점: 로그인 `detail`에 영역은 없다(영역은 계획 35).
- 읽기 API: `GET /api/v1/audit`(`audit::list_audit`, `AuditParams{since, until, user, node, action, limit}` `deny_unknown_fields`). 거절 순서 401 → 403(admin 아님, `ApiError::forbidden`) → 400 `invalid_request`(시각이 밀리초도 RFC 3339도 아님, `limit`이 1~5000 밖). `since > until`은 빈 목록. 설계와 다른 점: 위트니스는 API가 없어 감사 로그도 없으므로 `NodeSpec.witness`인 멤버는 묻지 않는다(`unreachable`에도 넣지 않음). 이름은 Node 리소스의 이름, 없으면 노드 id 문자열. 자기 노드는 `state.audit.read`(실패하면 `unreachable`), 다른 노드는 `Peers::read_audit`를 노드마다 5초 제한으로 동시에. 오류·제한 시간·`peers` 없음·`ReadAudit`이 없는 옛 opld(unimplemented)는 `unreachable`(정렬), 감사 로그를 끈 노드는 응답의 `disabled`(정렬 — 설계에 없음)다: 이 노드는 `AuditLog::is_enabled`로, 다른 노드는 `ReadAudit`의 `failed_precondition`으로 안다. 합친 뒤 `(time, id)` 내림차순, `limit`을 넘으면 자르고 `truncated`.
- 노드 사이 RPC: `build.rs`의 JSON 메서드 `ReadAudit`(`AuditQuery` → `opl_peer::AuditReply{entries}`), 트레이트 `opl_peer::AuditSource`(async_trait, `MigrationReceiver` 모양, `Result<Vec<AuditEntry>, String>`), `PeerService::with_audit(Arc<dyn AuditSource>)`(없으면 `Status::unimplemented`, `AuditSource::enabled`(기본 참)가 거짓이면 `Status::failed_precondition("audit log disabled")`, 받는 쪽이 `limit`을 5000으로 자름), `Peers::read_audit(addr, query, timeout)`(꺼진 노드면 `Ok(None)`). opld는 끈 노드에도 `AuditLog::disabled`를 넘긴다. `AuditLog`가 `AuditSource`를 구현한다.
- opld `[audit]`(`AuditSection`): 설계의 `max_file_size` 대신 `max_file_mib`(기본 16)이고 `enabled`(true)·`max_files`(8). `max_file_mib`가 0이거나 256을 넘거나(읽기가 파일을 통째로 메모리에 올림) `max_files`가 0이면 시작 오류, 모르는 키도 오류(`deny_unknown_fields`). `audit_config(data_dir, node)`가 `{data_dir}/audit`의 설정(꺼졌으면 None). `member.rs`는 감사 로그를 `PeerService`보다 먼저 열어(열지 못하면 시작 오류) `AppState.audit`과 `PeerService::with_audit`에 같은 `Arc<AuditLog>`를 넘기고, 종료 때 API를 멈춘 뒤 `shutdown`한다. opld의 tracing 출력은 stdout이 터미널일 때만 색 코드를 넣는다(journald로 가는 `opl_audit` 줄을 그대로 전달할 수 있게).
- oplctl `audit [--since] [--until] [--user] [--node] [--action] [--limit]`: 준 거르기만 쿼리에 넣고(없으면 서버 기본 24시간·200), `--since`의 `90s`·`30m`·`1h`·`7d`는 클라이언트가 지금에서 뺀 밀리초로, 그 밖(RFC 3339·밀리초)은 그대로 보내 서버가 푼다. 기간 `--since`와 `--until`을 함께 주면 보내지 않고 오류(`a relative --since cannot be combined with --until; give a time`). 표 `TIME`(UTC `YYYY-MM-DDTHH:MM:SSZ`)·`NODE`·`USER`·`IP`·`ACTION`·`TARGET`(`kind/key`, 없으면 `detail`, 둘 다 없으면 `-`)·`STATUS`, 표 뒤 stderr에 `warning: no audit records from: …`, `note: the audit log is disabled on: …`, `note: more entries match; narrow the range or raise --limit`, `-o json`은 응답 그대로이고 stderr에 쓰지 않는다.
- 웹: `web/src/audit/AuditPage.tsx`, 라우트 `/audit`, 메뉴 항목의 `admin?: boolean`(admin에게만 보임 — 다른 역할이 주소로 오면 읽지 않고 "관리자만" 안내), i18n `nav.audit`·`audit.*`. 범위는 `since`만 보내(읽을 때의 지금에서 뺀 밀리초) 새로고침이 창을 앞으로 민다. 사용자·동작은 적용을 눌러야, 다듬어 비어 있지 않을 때만 보낸다. 노드 거르기는 없다. 대상 열은 target이 없으면 detail, `disabled`는 정보 색 안내(`audit.disabled`), 데이터가 있는데 다시 읽기가 실패하면 표 위에 오류(`audit.refreshFailed`).
- 시험: opl-types 단위(`matches`의 범위 경계·사용자·action·path 부분 문자열), `opl_api::audit` 단위(쓰고 읽기, 0600·0700, 크기·개수 회전과 가장 오래된 것 지움, 새 것부터·거르기·`limit + 1`, 망가진 줄, 파일 순서로 멈춤, 비공개 `AuditLog::start(cfg, capacity, gate)`로 채운 채널 뒤 `audit.dropped`, disabled, `target`, 필드 512바이트 자르기, 인증 없는 항목의 IP별 한도와 `audit.suppressed`, 새 요청 없이 끝난 창의 수가 1초 틱에 적힘(61초 전 시계), 훑기는 끝난 창만, IPv6 /64, 1만 IP에서 가장 오래된 창 축출, 두 파일의 같은 `id` 한 번, `max_files` 넘는 옛 파일 지움, 0700·0600으로 맞추기와 링크 거절, 쓰기 스레드가 막힌 채 `shutdown`이 마감 뒤 돌아오고 런타임을 떨어뜨려도 끝남), `opl-api/tests/audit.rs`(시험 `Env`는 늘 `{dir}/audit`에 노드 "node1"·1 MiB·2개의 감사 로그: 주체·auth·템플릿·target·status, 403·401·틀린 토큰, 로그인 성공·실패·`<invalid>`와 비밀번호가 파일에 없음, 로그아웃, GET은 안 적고 콘솔 GET은 적음, 쿼리가 path에 없음, 구독 `id=`, `GET /audit`의 권한·시각·limit 경계·거르기·truncated, 감사 로그를 끈 이 노드는 `disabled`), `opl-peer/tests/grpc.rs`(`ReadAudit`·unimplemented·limit 자르기), `two_nodes.rs`(두 노드 합치기, 한 노드를 멈춘 뒤 `unreachable`, 감사 로그를 끈 다른 노드는 `unreachable`이 아니라 `disabled`), opld 설정 단위(`max_file_mib` 256·257), oplctl `fake_api`(`disabled` 안내, TARGET의 detail, 기간 `--since`와 `--until`을 함께 주면 오류), opld E2E `crates/opld/tests/audit.rs`(노드 셋 중 `[audit] enabled = false` 하나 — 노드마다 바꾸는 요청 뒤 한 노드의 `oplctl -o json audit`가 두 노드 기록을 함께 보이고 `unreachable` 없음, `--node`, 표, `audit.log` 0600, 꺼진 노드는 디렉터리 없고 `disabled`에 있음), 웹 Vitest(`AuditPage.test.tsx` — 다른 역할은 요청 없음, 데이터가 있을 때 다시 읽기 오류, `disabled` 안내, 대상 열 detail — 와 메뉴).

## 3. 인증 영역과 LDAP (계획 35)

### 3.1 영역

- 새 리소스 `Realm`(이름 = 영역 이름, 소문자 이름 규칙, `local`은 예약). spec은 종류별 enum `RealmSpec { display: Option<String>, backend: RealmBackend, roles: RoleMapping }`, `RealmBackend::Ldap(LdapRealm)`(계획 35), `RealmBackend::Oidc(OidcRealm)`(계획 36). 비밀(`bind_password`, `client_secret`)은 API 응답·watch에서 지운다(설정의 구독 키와 같은 방식, `has_bind_password: true`로만 보임).
- `RoleMapping { groups: Vec<{ group: String, role: Role }>, default: Option<Role> }`: 사용자의 그룹 가운데 맞는 것들 중 가장 높은 역할(admin > operator > viewer), 없으면 `default`, 그것도 없으면 로그인 거절(403 `no_role`).
- `Realm`을 만들고 고치고 지우는 것은 admin. 새 Kind라 쓰기 전에 `require_current`(옛 노드는 새 Kind의 명령을 풀지 못함).
- `GET /api/v1/auth/realms`(인증 없음): 로그인 화면용 `[{ name, display, kind }]`, 맨 앞에 `local`.

### 3.2 외부 사용자

- 이름은 `<사용자>@<영역>`(사용자 부분은 소문자로 바꾼 1~64자 `[a-z0-9._-]`, 이것이 아니면 거절). `validate_name`을 쓰는 로컬 사용자 만들기 API는 그대로이고, 외부 사용자 이름은 `validate_external_name`.
- `UserSpec.realm: Option<String>`(None이면 직렬화하지 않음), 외부 사용자의 `password_hash`는 빈 문자열이고 로컬 로그인 경로에서 늘 실패한다. 외부 사용자의 비밀번호는 API로 바꿀 수 없다(400 `external_user`).
- 로그인에 성공하면 `User`를 만들거나(첫 로그인) 역할이 바뀌었으면 고친다. 역할이 바뀌면 `session_epoch`도 올린다. 관리자가 외부 사용자를 지울 수 있고, 다음 로그인에 다시 생긴다. 외부 사용자도 API 토큰을 만들 수 있다. 토큰은 디렉터리에서 사용자를 지워도 남는다(관리자가 지움 — 한계로 적음).
- 영역을 지우면 그 영역 사용자의 세션은 다음 요청에서 끊고(사용자를 읽을 때 영역이 없으면 401), `User`·토큰은 남긴다(다시 만들면 이어 씀).

### 3.3 로그인

- `POST /auth/login { username, password, realm? }`: `realm`이 없거나 `local`이면 지금 그대로. LDAP 영역이면 시도 제한(키는 `<사용자>@<영역>`과 IP) → LDAP 확인 → `User` 만들기·고치기 → 세션. OIDC 영역이면 400(`/auth/oidc/...`를 써야 함).
- LDAP 확인(`LdapRealm { url, bind_dn: Option, bind_password: Option, base_dn, user_filter, group_attr, ca_pem: Option, timeout }`):
  1. `ldaps://`이거나 `ldap://`이면 StartTLS가 반드시(평문 바인드는 하지 않음). `ca_pem`이 있으면 그것만 믿고 없으면 시스템 루트.
  2. 서비스 계정으로 바인드(없으면 익명) → `base_dn` 아래에서 `user_filter`(기본 `(&(objectClass=person)(uid={username}))`, `{username}`은 RFC 4515 이스케이프)로 정확히 한 항목을 찾음(0개·2개 이상은 실패).
  3. 찾은 DN과 사용자 비밀번호로 다시 바인드(빈 비밀번호는 거절 — 익명 바인드로 통과하는 것을 막음).
  4. 그룹: 항목의 `group_attr`(기본 `memberOf`) 값(DN)들을 `RoleMapping.groups`의 `group`과 대소문자 무시로 비교.
  - 실패는 모두 401 `invalid_credentials`로 같고, 서버에 닿지 못하거나 서비스 바인드가 실패하면 503 `realm_unavailable`(로그에 원인).
- `POST /api/v1/realms/{key}/actions/test { username, password }`(admin): 위 과정을 돌려 단계별 결과(서비스 바인드, 찾은 DN, 그룹, 정해질 역할)를 돌려준다. `User`는 만들지 않는다.

### 3.4 oplctl과 웹

- `oplctl realm list|show|add-ldap|set|remove|test`, `oplctl login --realm <이름>`(비밀번호 로그인과 같이 토큰을 만듦).
- 웹 로그인 화면에 영역 고르기(영역이 `local`뿐이면 숨김). 설정 아래 "인증 영역" 화면(admin): 목록, LDAP 영역 만들기·고치기, 역할 매핑 표, 시험 대화상자. 사용자 목록에 영역 열.

### 3.5 시험

- 단위: 이름 규칙, 필터 이스케이프, 역할 매핑(가장 높은 역할·기본·없음).
- API: `tests/common/ldap.rs`의 가짜 LDAP 서버(`lber`로 Bind·Search·Unbind·ExtendedRequest(StartTLS)만, 시험 CA 인증서로 TLS): 첫 로그인에 사용자 생김·역할, 그룹이 바뀌면 역할과 세션 세대, 틀린 비밀번호·빈 비밀번호·없는 사용자·두 항목, 서버 없음 503, 시도 제한, 비밀이 응답·watch에 없음, 권한, 옛 노드 409, 영역 지우기와 세션, 시험 동작.
- CI Linux 기능 `ldap-it`: apt의 slapd로 실제 LDAPS·StartTLS 로그인.
- 웹 Vitest: 로그인의 영역 고르기, 영역 화면.

### 3.6 구현(계획 35)

- 타입(`opl_types::realm`): `Realm = Resource<RealmSpec, RealmStatus>`, `Kind::Realm`(`"realm"`), `RealmSpec{display, backend, roles}`(`deny_unknown_fields`, `display`는 None이면 쓰지 않고 `roles`는 serde 기본값), `RealmBackend::Ldap(LdapRealm)`(`#[serde(tag = "kind", rename_all = "snake_case")]`), `LdapRealm{url, bind_dn, bind_password, base_dn, user_filter, group_attr, ca_pem, timeout_secs}`(`DEFAULT_USER_FILTER` `(&(objectClass=person)(uid={username}))`·`DEFAULT_GROUP_ATTR` `memberOf`·`DEFAULT_TIMEOUT_SECS` 10이 serde 기본값, `deny_unknown_fields`), `RoleMapping{groups: Vec<GroupRole{group, role}>, default}`와 `role_for(&[String])`(앞뒤 공백을 떼고 ASCII 대소문자 무시, 맞는 것 중 가장 높은 역할, 맞는 매핑이 있으면 `default`보다 우선, 없으면 `default`). `RealmSpec::validate() -> Result<(), RealmError>`: URL은 `ldap://`·`ldaps://`에 호스트(IPv6 `[…]` 포함), `base_dn`·`group_attr` 비어 있지 않음, `user_filter`에 `{username}` 정확히 한 번, `bind_password`는 `bind_dn`이 있어야, `bind_dn`에는 비어 있지 않은 `bind_password`가 있어야(`BindDnWithoutPassword` "bind_dn needs bind_password; remove bind_dn for an anonymous search" — 익명 검색은 둘 다 없을 때만), `timeout_secs` 1~30(전체 마감 `timeout_secs × 4 + 1초`가 최대 121초), 그룹 매핑의 `group` 비어 있지 않음. `validate_realm_name`(리소스 이름 규칙, `LOCAL_REALM` `"local"` 예약, UUID로 풀리는 이름은 `LooksLikeId` "invalid name …: names must not look like an id" — API가 id로 읽어 이름으로 부를 수 없음). `RealmError`의 영어 문구가 400 `invalid_request`의 메시지다. 설계와 다른 점: 설계의 `timeout`은 `timeout_secs`. openapi 기능에서 realm 타입에 `ToSchema`. `LdapRealm`의 `Debug`는 손으로 써서 `bind_password`를 `Some("***")`로 가린다(그것을 담은 `RealmSpec`·`RealmRequest`도).
- 사용자(`opl_types::auth`): `UserSpec.realm: Option<String>`(None이면 쓰지 않아 로컬 사용자는 계획 34의 JSON 그대로 — 옛 노드가 읽음), 외부 사용자의 `password_hash`는 `""`(argon2 PHC가 아니라 로컬 확인은 패닉 없이 늘 실패). `validate_external_name`(`<사용자>@<영역>`, 사용자 부분 1~64자 `[a-z0-9._-]`, 영역 부분 `validate_name`), `external_name(user, realm)`(사용자 부분을 ASCII 소문자로 바꾼 뒤 검사, 오류는 기존 `NameError` — 문구가 로컬 이름용이라 사용자에게 보이지 않음).
- 영역 API(`opl_api::realms`): `GET`·`POST /api/v1/realms`, `GET`·`PUT`·`DELETE /api/v1/realms/{key}`(tag `auth`). 본문 `RealmRequest{name?, display?, backend, roles}`(POST·PUT 공용, `deny_unknown_fields`; `name`은 만들 때 필요하고 바꿀 때 주면 지금 이름과 같아야 함; 빈 `display`는 None). 응답 `RealmView{id, name, revision, display?, backend: RealmBackendView::Ldap(LdapRealmView{…, has_bind_password}), roles}`. 만들기·바꾸기 모두 저장·비교 전에 `url`·`bind_dn`의 앞뒤 공백을 떼고 `ca_pem`은 CRLF를 LF로 바꿔 앞뒤 공백을 뗀다(끝 줄바꿈이 있는 `--ca-file` CA와 웹이 다듬어 보낸 같은 CA를 같은 값으로 봄). `PUT`은 통째로 바꾼다: `backend.bind_password`를 빼면 저장된 값을 두는데 `url`·`bind_dn`·`ca_pem`이 모두 그대로일 때만이고, 저장된 비밀번호가 있는데 하나라도 바뀌었으면 400 `invalid_request`("bind_password must be given again when url, bind_dn or ca_pem changes" — 저장된 비밀번호를 다른 서버·계정으로 보내지 않음), `""`이면 지움(그러면 `bind_dn`도 없어야 검증을 통과). 바뀐 것이 없으면 쓰지 않고 200. `If-Match`가 다르면 412, 없으면 읽은 revision에 쓰고 충돌하면 다시 읽어 되풀이(보안 그룹과 같음, 10번 넘으면 409 `busy`). 쓰기(POST·PUT·DELETE)는 모두 `require_current` 뒤. 권한: `RoleAuthorizer`의 계정 종류(`User|ApiToken|JoinToken`)에 `Kind::Realm`을 더해 읽기·쓰기 모두 admin만(웹 `permissions.ts`도 같게). `Realm`은 `WATCH_KINDS`에 넣지 않는다(설계의 "watch에서 지움" 대신 — 웹은 바꾼 뒤 다시 읽음). `GET /api/v1/auth/realms`(`security(())`): `RealmSummary{name, display(null 가능), kind: RealmKind(local|ldap)}`, `local`이 먼저, 나머지는 이름 순.
- LDAP 클라이언트(`opl_api::ldap`, 워크스페이스 의존 `ldap3` 0.12.1 `default-features = false, features = ["tls-rustls-ring"]` — 새 패키지는 `ldap3`·`lber`·`rustls-native-certs`뿐): `authenticate(&LdapRealm, username, password) -> Result<LdapUser{dn, groups}, LdapError{InvalidCredentials, Unavailable(String)}>`. 빈 비밀번호는 연결하지 않고 `InvalidCredentials`. 연결은 `LdapConnSettings::set_starttls(true)`(`ldap://`는 StartTLS, `ldaps://`는 처음부터 TLS)와 `set_conn_timeout`, `ca_pem`이 있으면 `opl_peer::pki::certs`로 읽은 인증서만 루트인 rustls(ring) 설정, 없으면 ldap3 기본 설정(`rustls-native-certs`의 시스템 루트 — 리눅스에서 읽지 못하면 빈 목록이라 모든 연결이 실패). 호스트 이름 확인은 rustls 기본. 서비스 바인드(`bind_dn`이 없으면 생략 — 검증이 `bind_dn`에 비밀번호를 요구) 실패 → `Unavailable`. `base_dn` subtree 스트림 검색(`SearchOptions` `sizelimit(2)`·`timelimit(timeout_secs)`, 필터는 `user_filter`의 `{username}`을 `ldap3::ldap_escape`로, 속성은 `group_attr`만, `EntriesOnly`로 참조·중간 응답을 뺌): 둘째 항목에서 멈추고 `abandon`(서버가 크기 제한을 지키지 않아도), 항목이 정확히 1개가 아니거나 결과 코드 4(sizeLimitExceeded)면 `InvalidCredentials`, 그 밖의 검색 실패는 `Unavailable`. 사용자 바인드 결과 49는 `InvalidCredentials`, 그 밖은 `Unavailable`. 그룹은 속성 이름을 ASCII 대소문자 무시로 맞춘 값들. 모든 작업에 `timeout_secs`, 끝나면 unbind. `authenticate`와 `test` 전체는 `timeout_secs × 4 + 1초` 마감(`tokio::time::timeout`; 작업마다의 제한 안에 참조를 끝없이 보내는 서버 같은 경우)이고 넘으면 `Unavailable("timed out")`(`test`는 걸린 단계를 실패로 적음). `authenticate`가 `InvalidCredentials`로 끝나면 시작부터 적어도 300ms(`MIN_FAILURE`)가 되도록 기다린다(디렉터리가 300ms 안에 답하면 없는 사용자와 틀린 비밀번호의 시간 차를 가린다 — 더 느린 디렉터리에서는 차이가 남을 수 있음; `test`는 기다리지 않음). 설계와 다른 점: 검색 실패·사용자 바인드의 49가 아닌 실패·나쁜 `ca_pem`도 503이다.
- 시험 동작: `POST /api/v1/realms/{key}/actions/test`(`RealmTestRequest{username, password}`, 권한은 `Action::Operate` on `Realm` → admin만) → `ldap::test(&RealmSpec, …) -> RealmTestResult{steps: Vec<RealmTestStep{name, ok, message}>, dn, groups, role}`(단계 상수 `STEP_CONNECT`·`STEP_SERVICE_BIND`·`STEP_SEARCH`·`STEP_USER_BIND`·`STEP_GROUPS`, 실패한 단계에서 멈춤, `groups`·`role`은 모두 성공했을 때만). `authenticate`와 같은 흐름이지만 빈 비밀번호도 연결해 `user_bind` 단계에서 실패로 보인다. 사용자·세션을 만들지 않고 시도 제한에 세지 않으며 `require_current`도 보지 않는다(쓰지 않음). 비밀번호는 응답·로그·감사에 없다(`RealmTestRequest`의 `Debug`도 가림).
- 로그인(`users::login`): `LoginRequest.realm: Option<String>`(serde 기본값). 없거나 `"local"`이면 `login_local`(계획 34 그대로 — 외부 사용자 이름은 `validate_name`에서 401). 영역이면 `login_realm`: 감사 `detail`을 `username=<u> realm=<r>`(사용자 부분이 형식이 아니거나 영역이 이름 형식이 아니면 그 자리에 `<invalid>`)로 먼저 적고 → `external_name`이 안 되면 `begin_ip`·401 → 영역이 없으면 400 `invalid_request`("unknown realm …", 시도로 세지 않음) → `attempts.begin(<외부 이름>, ip)` → `ldap::authenticate`(디렉터리에는 소문자로 바꾼 사용자 부분을 물음): `InvalidCredentials`는 로컬과 같은 401 `invalid_credentials`, `Unavailable`은 `warn!`(원인) 뒤 503 `realm_unavailable`("the directory of realm <r> is unavailable") → `role_for`가 None이면 403 `no_role` → `require_current` → `upsert_external`(없으면 `User{realm: Some, password_hash: "", role}` 만들기, 역할이 다르면 역할과 `session_epoch += 1`, 같으면 쓰지 않음; `AlreadyExists`·`NameTaken`·`RevisionMismatch`는 다시 읽어 한 번 더 — 같은 사용자의 거의 동시 로그인 사이에 디렉터리 그룹이 바뀌면 옛 그룹을 읽은 쪽이 나중에 써서 역할이 되돌아갈 수 있다: 드문 경쟁이고 다음 로그인에 바로잡히므로 코드로 막지 않음) → `attempts.success`. 설계와 다른 점: 503·403·409도 시도 제한의 실패로 남는다(`begin`이 미리 센 것을 `success`로만 뺌). 세션 쿠키·감사 주체는 로컬과 같은 코드.
- 외부 사용자: `PUT /users/{key}`에 `password`가 있으면 400 `external_user`("the password of an external user is managed by its realm"), 역할은 바꿀 수 있으나 다음 로그인에 매핑으로 다시 정해짐. `UserView.realm`(None이면 쓰지 않음). `AppState::principal_for`와 세션·토큰 인증은 사용자의 `realm`이 있는데 그 `Realm`이 없으면 401(`realm_exists`) — 영역을 지우면 그 사용자의 세션·토큰이 모든 노드에서 멈추고, 같은 이름으로 다시 만들면 이어 쓴다. `delete_user`는 그대로(토큰도 지움).

## 4. OIDC SSO (계획 36)

### 4.1 설정

- `OidcRealm { issuer, client_id, client_secret: Option, scopes (기본 ["openid","profile","email"]), username_claim (기본 "preferred_username"), groups_claim (기본 "groups"), ca_pem: Option }`. 공개 클라이언트(비밀 없음)도 PKCE로 된다.
- 리디렉트 URI는 `https://<사용자가 연 노드 주소>/api/v1/auth/oidc/callback`. 노드마다 주소가 다르면 IdP에 모두 등록해야 한다(영역 화면이 이 노드의 값을 보여 줌).
- discovery(`<issuer>/.well-known/openid-configuration`)와 JWKS는 노드 메모리에 10분 둔다. 모르는 `kid`면 한 번 다시 받는다. issuer는 `https://`만(시험은 시험 CA).

### 4.2 흐름

1. 웹이 `GET /api/v1/auth/oidc/{realm}/start`로 간다(최상위 이동). 서버는 `state`·`nonce`·PKCE 검증자를 만들어 쿠키 `opl_oidc`(HttpOnly, Secure, SameSite=Lax, 10분, `Path=/api/v1/auth/oidc`)에 넣고 — 값은 영역·state·nonce·검증자·만든 시각을 클러스터 CA 비밀 키(이미 모든 노드의 `ClusterSpec`에 있음)에서 HKDF-SHA256(정보 `opl-oidc-state`)으로 만든 키로 HMAC한 것 — 새 저장 값이 없고 어느 노드나 같은 키를 얻는다 — IdP의 authorization endpoint로 302.
2. IdP가 `/auth/oidc/callback?code&state`로 돌려보낸다. 서버는 쿠키를 확인(HMAC·10분·state 같음)하고 지운 뒤, token endpoint에 코드와 검증자로 교환한다(`client_secret_basic`, 비밀이 없으면 `client_id`만).
3. ID 토큰 확인: JWS `alg`는 RS256·ES256만(`none`·HS* 거절), JWKS의 키로 서명, `iss`·`aud`(client_id 포함, 여러 개면 `azp`)·`exp`·`iat`(5분 오차)·`nonce`.
4. 사용자 이름은 `username_claim`(소문자, 규칙에 맞지 않으면 실패), 그룹은 `groups_claim`(문자열 배열, 없으면 빈 것) → 역할. 클레임이 ID 토큰에 없으면 userinfo endpoint에서 한 번 더 읽는다.
5. `User` 만들기·고치기(3.2와 같음) → 세션 쿠키 → `/`로 302. 실패하면 `/login?error=<코드>`로 302(코드는 `sso_failed`·`no_role`·`realm_unavailable`), 원인은 로그와 감사 로그 `detail`에.
- 시도 제한: 콜백 실패도 IP 키로 센다.
- 로그아웃은 opLite 세션만 끝낸다(IdP 로그아웃 없음).

### 4.3 웹·oplctl

- 로그인 화면: OIDC 영역마다 "<표시 이름>으로 로그인" 버튼. `?error=` 문구.
- 영역 화면에 OIDC 만들기·고치기, 이 노드의 리디렉트 URI 보이기. `oplctl realm add-oidc`.

### 4.4 시험

- `tests/common/idp.rs`의 가짜 IdP(HTTPS, discovery·authorize(바로 코드로 돌려보냄)·token·jwks·userinfo, RS256·ES256 키): 성공 흐름(쿠키·세션), state 다름·쿠키 없음·쿠키 만료·HMAC 바뀜, nonce 다름, aud·iss·exp 틀림, `alg: none`, 모르는 kid 뒤 키 바뀜, 그룹 → 역할·`no_role`, userinfo로 클레임, 다른 노드로 돌아온 콜백(`two_nodes.rs`).
- 웹 Vitest: 버튼, 오류 문구.

### 4.5 구현(계획 36)

- 타입(`opl_types::realm`): `RealmBackend::Oidc(OidcRealm)`(`"kind": "oidc"`), `OidcRealm{issuer, client_id, client_secret, scopes, username_claim, groups_claim, ca_pem, timeout_secs}`(`deny_unknown_fields`, `client_secret`·`ca_pem`은 None이면 쓰지 않음, 기본값 `DEFAULT_SCOPES` `["openid","profile","email"]`·`DEFAULT_USERNAME_CLAIM` `preferred_username`·`DEFAULT_GROUPS_CLAIM` `groups`·`timeout_secs` 10, 손으로 쓴 `Debug`가 `client_secret`을 가림). 검증(`RealmError`의 새 변형 `Issuer`·`ClientId`·`Scopes`·`UsernameClaim`·`GroupsClaim`·`OidcTimeout`): issuer는 호스트가 있는 `https://` URL이고 쿼리·조각·사용자 정보·공백이 없음(끝 `/`는 정규화하지 않고 그대로 비교에 씀), `client_id`·두 클레임 이름은 공백만이 아님, `scopes`에 `openid`가 있고 값마다 공백 없는 비어 있지 않은 글, `timeout_secs` 1~30(LDAP과 같게). 계획 35의 반박 불가 패턴(`let RealmBackend::Ldap(l) = …`)은 match로. `opl_types::auth`: `UserSpec.subject: Option<String>`(None이면 쓰지 않음 — 옛 노드가 모르는 필드라 쓰기 전 `require_current`), OIDC 외부 사용자를 처음 만든 IdP 사용자 `"<iss> <sub>"`(공백 하나). 외부 사용자 이름은 마지막 `@`에서 영역을 나누고(`rsplit_once`) 사용자 부분 규칙은 영역 종류에 따라: LDAP은 `validate_external_name`·`external_name`(1~64자 `[a-z0-9._-]`, 그대로), OIDC는 `validate_oidc_external_name`·`external_name_oidc`(1~128자 `[a-z0-9._+-]`와 안쪽 `@` 하나 — 앞뒤 비어 있지 않음; `alice@corp.com@okta`는 사용자 `alice@corp.com`·영역 `okta`). 로컬 사용자(`POST /users`)는 그대로 `@` 불가. 설계와 다른 점: `timeout_secs`가 더해졌고, 사용자 이름 규칙이 OIDC에서 넓어졌다(이메일 모양).
- 영역 API(`opl_api::realms`): `RealmBackendView::Oidc(OidcRealmView{issuer, client_id, scopes, username_claim, groups_claim, ca_pem?, timeout_secs, has_client_secret})`, `RealmKind::Oidc`(`GET /auth/realms`의 `kind` `oidc`). `spec_of`가 종류마다 `ldap_of`·`oidc_of`로 나뉘고 `trim_pem`을 함께 쓴다. `oidc_of`는 `issuer`·`client_id`의 앞뒤 공백을 떼고 `ca_pem`을 다듬은 뒤, `client_secret`을 빼면 저장된 OIDC 영역에 비밀이 있을 때 `issuer`·`client_id`·`ca_pem`이 모두 그대로일 때만 두고 아니면 400 "client_secret must be given again when issuer, client_id or ca_pem changes"(저장된 비밀이 없으면 공개 클라이언트로 남음), `""`는 지움. 종류를 바꾸는 `PUT`은 비밀을 옮기지 않는다. `POST /auth/login`은 영역을 먼저 읽어 OIDC 영역이면 이름 규칙과 관계없이(이메일 모양 이름도) 시도로 세기 전에 400 `invalid_request` "realm <r> signs in through its identity provider". 시험 동작: `RealmTestRequest{username?, password?}`(둘 다 선택), 본문은 없어도·`null`이어도 됨(`crate::error::Json`에 `OptionalFromRequest` — `Content-Type`이 없으면 None), LDAP 영역은 둘 중 하나라도 없으면 400 "username and password are required to test an LDAP realm", OIDC 영역은 본문을 무시하고 `oidc::test`.
- OIDC 모듈(`opl_api::oidc`, pub; opl-api에 `ring`·`base64` 직접 의존과 reqwest `form` 기능 — 새 패키지 없음): `client(&OidcRealm)`(reqwest native-tls, 리다이렉트 없음, `https_only`, 시간 제한 `timeout_secs`, `ca_pem`이 있으면 `tls_certs_only`로 그 인증서만 — 읽지 못하거나 비면 `Invalid`), 응답 본문은 읽으며 1MiB까지(`content_length()`가 넘으면 바로, 아니면 `chunk()`로 읽다가 넘으면 멈춤 — `Invalid`). `OidcError{Unavailable(→realm_unavailable: 연결·TLS·시간 제한·2xx가 아닌 응답 — 오류 본문의 `error`를 붙임), Invalid(→sso_failed: 토큰 끝점 4xx의 `invalid_grant`와 액세스 토큰을 보낸 userinfo의 401·403도)}`. `discovery_url`(issuer 끝 `/`를 하나로 합쳐 `/.well-known/openid-configuration`), `fetch_discovery`(`Discovery{issuer, authorization_endpoint, token_endpoint, jwks_uri, userinfo_endpoint?}`, `issuer`가 설정값과 글자 그대로 같고 끝점은 `https://`), `parse_jwks`(`kty: RSA`(`n`,`e`)·`kty: EC` `crv: P-256`(`x`,`y` → `04||x||y`)만, `alg`가 있으면 RS256·ES256, `use`가 있으면 `sig`, 깨진 키는 건너뜀), `verify_id_token(token, keys, Expected{issuer, client_id, nonce}, now)`(헤더 `alg`는 RS256(`RSA_PKCS1_2048_8192_SHA256`)·ES256(`ECDSA_P256_SHA256_FIXED`)만, 헤더에 `crit`가 있으면 거절, `kid`가 있으면 그 kid의 키(JWKS에 그 kid가 없으면 kid 없는 키 가운데 alg가 맞는 것), 없으면 alg가 맞는 키를 모두; ## 5. 원격 클러스터 (계획 37)

### 5.1 리소스

- 새 리소스 `Remote`(이름은 사용자가 붙임): `RemoteSpec { url, ca_fingerprint, token }`(token은 원격 클러스터에서 만든 API 토큰, 응답·watch에서 지움), `RemoteStatus { reachable, checked_at, error, cluster_name, version, nodes: {total, online}, vms: {total, running}, cpus, memory_gib }`.
- 만들 때(admin, `require_current`) 서버가 바로 연결해 본다: `GET <url>/api/v1/cluster/ca`의 CA 지문이 `ca_fingerprint`와 같은지(다르면 400 `remote_fingerprint_mismatch`), 그 CA로 TLS를 믿고 토큰으로 `GET /auth/whoami`(401이면 400 `remote_unauthorized`). 자기 클러스터(같은 CA 지문)는 400 `remote_is_local`.
- 연결은 그 CA 하나만 믿는 rustls 클라이언트(호스트 이름은 확인하지 않고 CA 서명만 — 노드 인증서의 이름은 노드마다 다름), 시간 제한 10초, 리다이렉트 없음.

### 5.2 상태 수집

- 리더의 `RemotePoller`(`TelemetryReporter`와 같은 모양): 30초마다(opld `[remotes] interval`) 원격마다 `GET /cluster`, `/nodes`, `/vms`를 읽어 상태를 계산하고, 바뀌었을 때만 `update_status`(같으면 쓰지 않음 — Raft 부하). `checked_at`은 상태가 바뀔 때만 바뀌므로, 웹은 `reachable`과 `error`만 믿는다.

### 5.3 중계

- `/api/v1/remotes/{key}/api/{*path}`: 그 원격의 `/api/v1/{path}`로 메서드·쿼리·본문·`Content-Type`·`If-Match`를 그대로 보내고 응답을 그대로 돌려준다(스트리밍, 본문 한도 없음). `Authorization`은 저장한 토큰으로 바꾸고, 쿠키·`Origin` 등은 보내지 않는다.
- 권한: `GET`은 로그인한 누구나(Remote 읽기), 그 밖은 admin. 원격 쪽 권한은 토큰 주인의 역할이 한 번 더 정한다(관리자는 viewer 토큰을 등록해 읽기만 하게 할 수 있음).
- `watch`·콘솔(WebSocket)은 중계하지 않는다(404 `remote_path_unsupported`).
- 중계한 바꾸는 요청은 이 클러스터의 감사 로그에 `action: remote.proxy`, `target: remote/<이름>`, `detail: <메서드> <경로>`로 남는다(원격 쪽에는 토큰 주인으로 남음).

### 5.4 oplctl과 웹

- `oplctl remote add <이름> --url --ca-fingerprint --token-file|- `, `list`, `show`, `remove`, `oplctl remote vms <이름>`, `oplctl remote vm <이름> start|stop|shutdown <VM>`.
- 웹 "원격 클러스터"(메뉴): 카드 목록(이름, 클러스터 이름, 버전, 노드 online/total, VM running/total, CPU·메모리, 닿지 않으면 오류), admin은 추가(지문은 CA를 먼저 받아 보여 주고 확인)·삭제. 카드를 누르면 그 클러스터의 VM 목록(중계로 읽음, 10초마다), admin은 시작·끄기·종료.

### 5.5 시험

- API: 두 `Env`(서로 다른 클러스터)로 등록(지문 틀림·토큰 틀림·자기 자신), 비밀이 응답에 없음, 중계 GET·POST와 권한, 토큰이 원격에서 viewer면 원격이 403, watch 404, 상태 수집과 바뀔 때만 쓰기, 원격이 꺼짐.
- opld E2E: opld 클러스터 둘(각 한 노드), 한쪽에 다른 쪽을 등록 → 상태 `reachable`, `oplctl remote vms`.
- 웹 Vitest: 카드, 추가 대화상자, VM 목록·동작 권한.

### 5.6 구현(계획 37)

- 타입(`opl_types::remote`): `Remote = Resource<RemoteSpec, RemoteStatus>`, `Kind::Remote`(`"remote"`). `RemoteSpec{url, ca_fingerprint, token, ca_pem}`(`deny_unknown_fields`, 손으로 쓴 `Debug`가 `token`을 가리고 `ca_pem`은 뺌). `ca_pem`은 등록·바꾸기 때 서버가 받아 지문을 확인한 원격 CA 인증서(PEM, 정확히 하나)로, 노드는 연결할 때 이것만 믿는다(설계 §5.1과 계획 37 스테이지 결정의 "CA PEM은 spec에 두지 않고 연결할 때마다 `fetch_ca`·노드 캐시"에서 바꿈 — 리뷰: 검증 없는 CA 받기를 등록 때 한 번으로). `normalize()`가 `normalize_url`(`https://<호스트>[:포트]` — 경로는 없거나 `/`, 쿼리·조각·사용자 정보·공백 없음, 포트 1~65535, IPv6는 `[주소]`, 앞뒤 공백과 끝 `/`를 뗌), `normalize_ca_fingerprint`(접두 `sha256:`는 선택·대소문자 무시, `AB:CD:…` 구분을 받아 `sha256:<소문자 64자>`), `token_id`(`opl_<uuid>_<공백 없는 ASCII 비밀>`의 id)를 이 순서로 검사하고 `RemoteSpecError{Url, Fingerprint, Token}`. `RemoteStatus{reachable, checked_at, error, cluster_name, version, nodes: NodeCounts{total, online}, vms: VmCounts{total, running}, cpus, memory_gib}`(`serde(default)`). 두 Counts는 API 문서에서 텔레메트리 보고의 같은 이름 스키마에 덮이지 않게 `RemoteNodeCounts`·`RemoteVmCounts`로 이름을 줌.
- 원격 클라이언트(`opl_api::remote_client`, pub; opl-api가 이미 쓰던 hyper·hyper-util·http-body-util·rustls·tokio-rustls — 새 패키지 없음): `fetch_ca(url)`(인증서를 검증하지 않는 `AnyCert` — 핸드셰이크 서명은 확인 — 로 `GET /api/v1/cluster/ca`, 2xx·64 KiB·정확히 인증서 하나인 PEM 확인; 지문 비교는 부르는 쪽. 아무 주소에나 연결하므로 원격이 준 말을 옮기지 않음: 2xx가 아니면 `Status(코드, 상태 이름)`, 연결 실패는 `Unreachable("cannot connect")`(시간 제한 문구는 그대로), TLS는 `Tls("TLS handshake failed")`, PEM 인증서가 아니면 `Invalid("… not an opLite cluster …")`), `RemoteClient::new(url, ca_pem, token)`(정확히 인증서 하나인 그 CA만 루트로 한 — 둘 이상이면 `Invalid`, 첫 인증서의 지문만 맞고 덧붙인 CA가 서명한 서버를 믿게 되지 않게 — `WebPkiServerVerifier`를 감싼 `AnyName`이 `CertificateError::NotValidForName`·`NotValidForNameContext`만 받아들임 — 서명·기간은 그대로 확인; IP 주소면 SNI 없음), `get_json(path)`(Accept JSON, 2xx가 아니면 `Status`, 4 MiB), `request(method, path_and_query, headers, body)`(`Host`·`Authorization: Bearer`를 채우고 상태와 관계없이 응답을 그대로 `Response<RemoteBody>`로; 보내고 받는 본문을 흘려 보내며 조각 사이 60초 `IdleTimeout`). 경로는 `/api/v1` 아래 상대, 요청마다 새 HTTP/1.1 연결, TCP·TLS 10초, 본문을 다 보낸 뒤 응답 헤더 10초, 리다이렉트를 따르지 않음(3xx 그대로). `RemoteError{Unreachable, Tls, Status(코드, 오류 본문의 message 또는 상태 이름 — `fetch_ca`는 상태 이름만), Invalid}`. 노드 메모리의 CA 캐시는 없다(spec의 `ca_pem`으로 `RemoteClient::new`).
- API(`opl_api::remotes`): `GET`·`POST /remotes`, `GET`·`PUT`(If-Match 선택 — 없으면 읽은 revision으로 쓰고 그 사이 바뀌면 다시 읽어 10번까지; 확인을 마친 뒤 쓸 때 revision이 달라도 저장된 spec이 확인 전에 읽은 것과 같으면(상태만 바뀜 — 수집기 따위) 다시 확인하지 않고 새 revision에 씀 — If-Match가 맞았던 요청도 200, 412는 그 사이 spec이 바뀐 때만)·`DELETE /remotes/{key}`. 읽기는 `Action::Read`(viewer 이상), 쓰기는 `Action::Write`(admin — `RoleAuthorizer`는 그대로, operator 목록에 Remote 없음), 쓰기 전 `require_current`. 본문 `RemoteRequest{name?, url, ca_fingerprint, token?}`(`deny_unknown_fields`, `Debug`가 token을 가림). 확인 순서: 검증 400(url·지문 정규화, token 모양, 이름 규칙, 이름 `probe` 거절 — `/remotes/probe`와 겹침) → 옛 노드 409 → `fetch_ca` 실패 502 `remote_unreachable` → 지문 다름 400 `remote_fingerprint_mismatch`(받은 지문을 메시지에) → 자기 클러스터 CA 400 `remote_is_local` → 받은 CA를 `spec.ca_pem`에 두고 그 CA로 `GET /auth/whoami`가 401이면 400 `remote_unauthorized`(그 밖 502) → 저장하고 곧 상태를 모아 씀. 확인 전체(`verify`)는 30초(`VERIFY_TIMEOUT`, 넘으면 502 `remote_unreachable` "timed out checking the remote cluster"), 만들기·바꾸기 직후의 상태 모으기와 refresh는 `COLLECT_TIMEOUT`(10초 — 넘으면 `reachable: false`). 그 상태를 적지 못하면(그 사이 수집기가 써 revision이 다름) 모은 기본값이 아니라 저장된 행을 다시 읽어 돌려줌(`recorded`). `PUT`은 통째로 바꾸고, `token`을 빼면 정규화한 url·ca_fingerprint가 모두 그대로일 때만 저장된 토큰을 둠(아니면 400 "token must be given again when url or ca_fingerprint changes"), url·ca_fingerprint가 그대로면 저장한 `ca_pem`도 두고 토큰만 확인하며(CA를 다시 받지 않음) 바뀌면 CA를 다시 받아 확인·저장, 이름은 바꾸지 못함, 같은 spec이면 쓰지 않음(확인도 안 함). 응답 `RemoteView{id, name, revision, url, ca_fingerprint, token_id, status}`(token·ca_pem 없음), `WATCH_KINDS`에 넣지 않음. 설계에 없던 끝점 둘: `POST /remotes/probe {url}`(admin — 웹이 등록 전에 지문을 보여 주려고: 브라우저는 다른 출처의 CA를 읽지 못함; 정규화한 `url`과 `ca_fingerprint`, 실패 502 — CA 받기도 `VERIFY_TIMEOUT`(30초, 넘으면 502 `remote_unreachable` "timed out checking the remote cluster")), `POST /remotes/{key}/actions/refresh`(admin — 곧 다시 모아 돌려줌).
- 상태 수집(`RemotePoller`·`RemotePollerConfig{tick, interval}`, `TelemetryReporter` 모양): 모든 노드에서 띄우고 리더만, `require_current`·`read_barrier` 뒤, `tick`마다 리더 메모리에 둔 마지막 수집 시각이 `interval`을 지난 원격을 동시에(각 10초 제한). `GET /cluster`·`/nodes`·`/vms`에서 필요한 필드만 읽어(원격 버전이 달라도 읽히게) cluster_name, version(위트니스를 포함한 노드 가운데 `opl_types::version::compare`로 가장 낮은 것), nodes total/online(위트니스 제외, online은 노드 status의 `online`)·cpus·memory_gib(위트니스 제외, MiB 합 / 1024), vms total/running(phase `running`). 실패면 `reachable: false`와 `error`만(나머지는 비움). 저장된 것과(`checked_at` 빼고) 같으면 쓰지 않고, 다르면 `checked_at`을 지금으로 `update_status_checked`(그 사이 바뀌었거나 지워졌으면 건너뜀). 리더가 바뀌면 기록을 비워 곧 모음.
- 중계(`opl_api::remote_proxy`): `/remotes/{key}/api/{*path}`를 `axum::routing::any`로 — **API 문서(OpenAPI)에 넣지 않음**(원격 API를 그대로 비추는 경로라 스키마가 없음; 웹은 업로드처럼 일반 `fetch`로 부름). 경로는 요청 URI에서 퍼센트 인코딩 그대로 잘라 조각마다 디코드한다. 권한: GET·HEAD이고 첫 조각이 허용 목록(`READABLE` — `vms`·`volumes`·`storage-pools`·`networks`·`security-groups`·`snapshots`·`backups`·`backup-jobs`·`vm-imports`·`nodes`·`tasks`·`cluster`·`version`·`settings`·`subscription`)이거나 경로가 정확히 `auth/whoami`면 `Action::Read`, 그 밖(`users`·`tokens`·`realms`·`audit`·`telemetry`·`remotes`(중계 사슬)·다른 `auth/*`·모르는 조각, 모든 쓰기)은 `Action::Write`(admin) — 설계 §5.3의 "GET은 누구나"에서 바꿈(리뷰: 원격 토큰이 admin이면 이 클러스터의 viewer가 원격의 사용자·토큰·감사 로그를 읽게 됨). 그다음 `.`·`..`·빈 조각이면 400, 첫 조각 `watch` 또는 `vms/<x>/console`(세 조각)이면 404 `remote_path_unsupported`, 원격을 찾고(404 `not_found`), 쿼리를 붙여 spec의 `ca_pem`으로 만든 클라이언트로 보냄(연결 실패 502 `remote_unreachable`). 보내는 헤더 `Content-Type`·`Content-Length`·`If-Match`·`Accept`, 돌려주는 헤더 `Content-Length`·`ETag`·`Retry-After`·`Content-Disposition`과 `Content-Type`(`application/json`(매개변수 허용)일 때만 그대로, 그 밖·없음은 `application/octet-stream`), 늘 `X-Content-Type-Options: nosniff`·`Content-Security-Policy: default-src 'none'; sandbox`(원격 본문이 이 출처의 페이지로 실행되지 않게). 원격의 401은 본문을 버리고 502 `remote_unauthorized` "the remote cluster refused the stored token; update it with `oplctl remote set --token-file`"(이 클러스터의 로그인 문제로 오해되지 않게 — 토큰 거절이 아닌 401, 예를 들어 중계한 `auth/login`의 틀린 비밀번호도 같게 보이지만 `auth/login`은 허용 목록 밖이라 admin만 닿으므로 받아들인 한계), 403 등 그 밖은 그대로. 감사는 설계의 `action: remote.proxy`가 아니라 계획 34 미들웨어 그대로(action `"<METHOD> /remotes/{key}/api/{*path}"`, target `remotes/<키>`, path는 실제 경로)이고 핸들러가 `AuditNote`로 detail `remote=<이름> <METHOD> /<경로>`. `vm_imports::esxi::percent_decode`를 crate 안에서 같이 씀.
- opld: `[remotes] interval`(기본 `"30s"`)·`tick`(기본 `"5s"`, `deny_unknown_fields`, 0 거절), `Services`에 `RemotePoller`(멈출 때 shutdown).
- oplctl: `remote list`(NAME·CLUSTER·VERSION·NODES online/total·VMS running/total·STATUS `reachable`|`unreachable: <이유>`), `show`(`키: 값` 줄 — token id, `changed at`(= `checked_at`), CPU·메모리), `add <이름> --url --token-file <파일|-> [--ca-fingerprint] [--yes]`(지문이 없으면 CLI가 직접 `fetch_ca`(client.rs의 것)로 받아 보이고 `--yes`·터미널 `[y/N]`·아니면 `--ca-fingerprint`로 다시 실행하라고 실패), `set <이름> [--url] [--ca-fingerprint] [--token-file]`(읽은 원격에 준 것만 바꿔 If-Match `PUT`, 토큰을 주지 않으면 빼서 옮기기 규칙은 서버가), `remove`, `refresh`, `vms <이름>`(중계 `GET /vms`, `vm list`와 같은 `VM_HEADERS` 표), `vm <이름> start|stop <VM> [--force]`(로컬 `vm stop`과 같은 이름 — `stop`은 ACPI `stop`, `--force`면 `stop?mode=force` 곧바로 끄기, `start --force`는 오류; 설계 §5.4의 `start|stop|shutdown`에서 바꿈; 원격 Task를 기다리지 않고 id만 보임). `add --token-file -`에 `--ca-fingerprint`도 `--yes`도 없으면 표준 입력을 읽거나 연결하기 전에 "reading the token from stdin needs --ca-fingerprint or --yes"(토큰을 읽은 표준 입력으로 확인을 물을 수 없음). 중계의 원격 거절은 502 `remote_unauthorized`라 서버 메시지를 그대로 보임(login 안내 없음).
- 웹(`web/src/remotes/`): 메뉴 `nav.remotes`(모두에게), `/remotes` 카드(이름 링크, 연결됨·연결 안 됨, URL, 클러스터 이름, 버전, 노드, VM, CPU, 메모리 GiB, 오류 문구, 10초마다 다시 읽음)와 admin 추가(URL → "CA 받기"(`probe`)가 지문을 보이고 URL을 정규화한 값으로 바꿈, 지문 확인 체크, 토큰)·고치기(저장된 URL·지문으로 시작, URL을 바꾸면 CA를 다시 받아 확인, 토큰을 비우면 빼서 보내되 URL·지문이 바뀌면 다시 요구, 상태 수집이 revision을 올리므로 If-Match 없이 `PUT`)·지우기·새로고침. `/remotes/<이름>`: 중계 `GET /vms`를 `proxy<T>()`(일반 `fetch`)로 10초마다, admin 동작 시작·정지(ACPI `stop`)·강제 정지(`stop?mode=force`, 확인 뒤), 상태로 막힌 동작은 로컬 VM과 같은 이유로 막음, 원격 Task는 지켜보지 않음. 중계 응답의 401은 이 클러스터의 세션 끝이므로 업로드처럼 `reportUnauthorized`(보낼 때의 인증 세대)로 알림(원격 거절은 502 `remote_unauthorized`라 기존 오류 문구). 추가 대화상자의 CA 지문은 `<dl>`(dt·dd). 오류 문구 `remote_unreachable`·`remote_fingerprint_mismatch`·`remote_is_local`·`remote_unauthorized`, ko·en.

## 6. 원격 복제 (계획 38)

### 6.1 받는 쪽 API

- `POST /api/v1/backups/receive { pool, manifest, origin }`(Backup 쓰기): 받는 풀(백업 풀)에 `Backup`을 phase `receiving`, `spec.origin = { cluster: <보낸 클러스터 이름>, ca_fingerprint, backup: <원본 id>, job: <원본 작업 이름> }`으로 만든다. 같은 `origin.ca_fingerprint`·`origin.backup`의 사본이 있으면 409 `replica_exists`(그 id를 `details`에).
- `PUT /api/v1/backups/{key}/files/{name}`(`name`은 매니페스트의 디스크 파일·`vars.fd`만): 본문을 `.part`에 쓰고 SHA-256을 응답 `{ sha256, size }`로 준다. 같은 파일을 다시 보내면 덮는다.
- `POST /api/v1/backups/{key}/actions/complete`: 모든 파일이 있으면 `manifest.json`을 쓰고 phase `ready`. 받는 중 24시간 손대지 않은 `receiving` 백업은 janitor가 지운다.
- 받은 사본은 그 클러스터의 보통 백업이다(목록·복원·지우기). `job`이 없으므로 받는 쪽 보존 규칙은 사본을 지우지 않는다.

### 6.2 보내는 쪽

- `BackupJobSpec.replicate: Option<{ remote, pool }>`(None이면 직렬화 안 함, 넣을 때 `require_current`). 작업이 만든 백업이 `ready`가 되면 리더의 스케줄러가 `backup-replicate` Task(대상 백업, 백업 풀을 읽을 수 있는 노드에서)를 만든다.
- Task: 원격(계획 37의 클라이언트, 저장한 토큰)에 `receive` → 파일마다 읽으면서 SHA-256을 계산해 `PUT`, 응답 해시가 다르면 실패 → `complete`. 결과를 원본 `BackupStatus.replicas: [{ remote, backup, state: ready|failed, error, at }]`에 적는다. 실패하면 다음 작업 실행 때 한 번 더(원본이 아직 있으면). 진행률은 Task 진행률.
- 수동: `POST /backups/{key}/actions/replicate { remote, pool }`(Backup 쓰기, 원격은 등록돼 있어야 함).
- 지우기: 보존 규칙이나 사용자가 원본을 지우면 `replicas`의 원격 사본도 지운다(원격 `DELETE /backups/{id}`, 404는 성공). 실패하면 원본 삭제는 그대로 하고 경고를 로그와 Task 오류에 남긴다(원격에 남은 사본은 원격에서 지움 — 한계).
- 원격 쪽 토큰 주인은 operator 이상이어야 한다(Backup 쓰기).

### 6.3 DR 절차(README)

1. 주 사이트 클러스터 A, DR 사이트 클러스터 B. B에 백업 풀을 만들고 operator 토큰을 만든다.
2. A에 B를 원격으로 등록하고, 백업 작업에 `replicate: { remote: B, pool: … }`.
3. A를 잃으면 B의 웹·oplctl에서 사본(출처 A)을 골라 복원한다(네트워크·보안 그룹은 B에 같은 이름이 있어야 하고, 없으면 복원 화면에서 바꿈 — 계획 27).

### 6.4 oplctl과 웹

- `oplctl backup-job set <이름> --replicate <원격>/<풀>|--no-replicate`, `oplctl backup replicate <백업> --remote --pool`, `oplctl backup list`에 출처·사본 열.
- 웹: 백업 작업 화면의 "원격 복제" 고르기, 백업 목록의 사본 상태와 출처, 백업 상세의 "원격으로 복제".

### 6.5 시험

- API: 두 `Env`로 받기 API(권한, 파일 이름 제한, 해시, 같은 출처 409, complete 조건, 받는 중 지우기), 작업 → 복제 Task → 원격에 ready 사본, 해시 다름 실패, 원본 지우면 원격 사본 지움, 원격 꺼짐의 실패와 다음 실행 때 다시, 원격 사본 복원.
- opld E2E: 클러스터 둘, 꺼진 VM 백업 복제 → B에서 복원해 같은 디스크 내용(가짜 하이퍼바이저·dir 풀).
- 웹 Vitest: 작업 화면, 목록 표시.

## 9. 알려진 틈

- 꺼진 노드의 감사 기록은 그 노드가 돌아와야 보이고, 디스크를 잃으면 사라진다(journald 전달로 보완). 루트 권한을 가진 사람은 파일을 고칠 수 있다(변조 방지 없음).
- (계획 34) 롤링 업그레이드 중 `ReadAudit`이 없는 옛 노드는 `GET /audit`의 `unreachable`이다. opld가 갑자기 죽으면 대기열에 남은 항목을, 전원이 나가면 fsync 전 마지막 1초쯤을 잃을 수 있고, 대기열이 차서 버린 항목은 `audit.dropped`의 수만 남는다(journald에도 없음). 파일 쓰기가 실패하면 `warn!`만 남기고 요청은 그대로 처리한다. 감사 로그를 끈 노드의 요청은 어디에도 남지 않는다(그 노드는 `disabled`로 보인다). 인증 없는 요청은 IP마다 1분에 60개까지만 적고 나머지는 `audit.suppressed`의 수만 남는다. 필드는 512바이트까지만 적는다. 로그인의 사용자 이름 칸에 비밀번호를 잘못 넣으면 이름 형식이면 `username=`에 그대로 적힌다. 읽기는 파일 하나를 통째로 메모리에 올리므로 `max_file_mib`는 256까지다. 콘솔은 연 것만 적는다(닫은 때·입력 없음). 리버스 프록시 뒤에서는 `ip`가 프록시 주소다(계획 13과 같음). 보존은 크기·개수로만 하고 날짜로 지우지 않는다.
- 외부 사용자를 디렉터리에서 지워도 이미 있는 세션(최대 12시간)과 API 토큰은 남는다.
- (계획 35) 영역을 지우고 같은 이름으로 다시 만들면 옛 영역 사용자의 세션(12시간 안)과 API 토큰이 지울 때의 역할로 되살아난다(새 영역이 다른 디렉터리를 가리켜도) — 다시 쓰기 전에 그 영역의 사용자를 지운다. 같은 사용자의 거의 동시 로그인 사이에 그룹이 바뀌면 역할이 옛 것으로 되돌아갈 수 있다(다음 로그인에 바로잡힘). 디렉터리는 로그인할 때만 보므로 그룹·계정 변화는 다음 로그인에 반영된다(바로 막으려면 opLite에서 사용자를 지움 — 토큰도 지워짐). 영역을 지워도 열린 콘솔(WebSocket)은 끊기지 않는다. 503 `realm_unavailable`·403 `no_role`도 시도 제한의 실패로 세므로 디렉터리가 멈춘 동안 되풀이한 로그인은 잠시 막힐 수 있다. 그룹은 사용자 항목의 속성 값만 보고(그룹 항목 찾기·중첩 그룹 풀기 없음) DN은 정규화 없이 문자열로 비교한다. 서버 주소는 하나이고 참조를 따라가지 않으며 단순 바인드만 한다. 사용자 부분이 `[a-z0-9._-]`(1~64자, 대문자는 소문자로)가 아닌 계정은 로그인할 수 없다. 시스템 루트를 읽지 못한 노드는 `ca_pem` 없는 영역에 연결하지 못한다. 서비스 계정 비밀번호는 Raft에 평문이다.
- 노드마다 주소가 다르면 IdP에 리디렉트 URI를 노드 수만큼 등록해야 한다.
- (계획 36) 리디렉트 URI는 `start` 요청의 `Host`로 만들고 scheme은 늘 https다(프록시 뒤면 프록시가 넘기는 Host). 로그아웃은 opLite 세션만 끝내고(IdP 로그아웃 없음), IdP의 계정·그룹 변화는 다음 로그인에 반영된다(이미 있는 세션 12시간·토큰은 남음). discovery·JWKS는 노드마다 10분 캐시라 IdP에서 지운 서명 키도 그동안 믿는다(영역을 고치면 새로 받음). 받기 실패는 15초 동안 기억하므로 IdP가 돌아와도 그동안은 같은 오류다. 토큰 끝점의 `invalid_grant`가 아닌 4xx(`invalid_client` 등 클라이언트 설정 잘못)도 `realm_unavailable`이라 IdP 장애와 같은 문구다(원인은 opld 로그). 롤링 업그레이드 중의 OIDC 로그인은 `sso_failed`(LDAP은 409). SSO 로그인은 늘 `/`로 돌아온다(`next`를 잃음). 외부 사용자는 처음 로그인한 IdP 사용자(`iss`·`sub`)에 묶이므로 IdP에서 계정을 다시 만들면(새 `sub`) 그 사용자의, 영역의 issuer를 바꾸거나 Entra ID에서 앱 등록을 바꾸면(새 `client_id` — Entra의 `sub`는 앱마다 다름) 모든 기존 사용자의 로그인이 `sso_failed`다(opLite에서 사용자를 지워야 함); `subject`가 없는 옛 사용자는 그 이름으로 처음 OIDC 로그인한 사람에게 묶인다. 이름 규칙(1~128자, 이메일 모양은 됨)에 맞지 않는 이름 클레임은 쓸 수 없고, 그룹은 클레임 값만 본다(Entra ID 그룹 초과 `_claim_names`는 그룹 없음). 클라이언트 인증은 `client_secret_basic`과 공개 클라이언트만, 서명은 RS256·ES256만이다. 클라이언트 비밀은 Raft에 평문이다. oplctl은 브라우저 SSO를 하지 않고 웹에서 만든 API 토큰을 `oplctl login --token-file`로 저장한다. OIDC 로그인은 시도 제한을 쓰지 않는다(맞힐 비밀이 없음). 시험 동작은 discovery·JWKS만 보고 클라이언트 비밀·리디렉트 URI·클레임은 확인하지 못한다.
- 원격 등록의 토큰은 Raft에 평문으로 있다(구독 키·바인드 비밀번호와 같음 — Raft 데이터는 노드의 루트만 읽음). 위트니스와 데이터 디렉터리 백업에도 있으므로 원격에는 필요한 만큼의 역할(보통 operator) 사용자의 토큰을 등록한다.
- (계획 37) 이 클러스터의 viewer·operator는 중계로 허용 목록의 자원(VM·볼륨·저장소·네트워크·보안 그룹·스냅숏·백업·가져오기·노드·Task·클러스터·버전·설정·구독과 `auth/whoami`)을 원격 토큰이 읽을 수 있는 만큼 읽는다(사용자·토큰·영역·감사·텔레메트리·원격의 원격은 admin만). 원격 URL은 노드 하나의 주소라 그 노드가 꺼지면 다른 노드가 살아 있어도 닿지 않는다(주소를 바꿈 — 토큰도 다시). 노드는 등록 때 저장한 CA만 믿으므로 원격 클러스터의 CA가 바뀌면 `remote set --ca-fingerprint`(토큰도 다시)로 고칠 때까지 닿지 않는다. `checked_at`은 상태가 바뀐 시각이라 마지막 확인 시각을 알 수 없다. watch·콘솔은 중계하지 않아 원격 VM은 10초마다 다시 읽고 원격 Task는 지켜보지 않는다. 원격 쪽 감사 기록은 토큰 주인으로 남는다(누가 요청했는지는 이 클러스터의 감사 로그에만). 원격을 지워도 원격 클러스터의 토큰은 남는다. 웹의 고치기는 If-Match 없이 보내 동시에 고치면 나중 것이 남는다. 수집 시각은 리더 메모리에만 있어 리더가 바뀌면 곧 다시 모은다.
- 복제는 전체 백업을 매번 보낸다(증분 없음). 원본을 지울 때 원격에 닿지 못하면 사본이 남는다.
