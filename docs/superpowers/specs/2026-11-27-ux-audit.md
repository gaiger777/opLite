## 0. 한눈에 — 핵심 진단 12개

1. **메뉴가 4단으로 깊다** [④⑦]. 구조는 사이드바 영역 6 → 영역 탭 33 → 보기 전환 27 → 화면 안 토글(경보 3, 지도 그림/목록, 만들기 폼/빌더, VM 상세 탭 10)이다. "네트워크" 탭 하나 아래 보기가 7개이고, "감사" 탭 아래에 "설정 기록"과 "선언 묶음"이 숨어 있다. 화면 이름만으로는 어디에 있는지 짐작할 수 없다(`layout/nav.ts:46-222`).
2. **같은 성격의 기능이 흩어져 있다** [⑦].
   - HA와 배치는 "보호"에 있고, 노드·클러스터는 "인프라"에 있다.
   - 원격 클러스터는 "보호 › 원격 복제"와 "설정 › 원격 클러스터" 두 곳에 있다.
   - 알림 대상은 "설정"에, 경보 규칙은 "활동 › 경보 › 규칙"에 있다.
   - 이미지·ISO는 "가상 머신"에, 볼륨은 "인프라"에 있다.
3. **입력 칸의 60%에 설명이 없다** [①]. `<Field>` 402개 가운데 240개에 `hint`가 없다. VM 쪽만 보면 88개 중 67개다. 설명이 있는 칸도 오류가 나면 설명을 감춘다(`components/Field.tsx:43` `hint && !error`). 칸 옆 "i" 도움말, 오른쪽 도움말 패널, 문서 링크가 하나도 없다. `EmptyState`의 `docsHref`는 쓰는 곳이 0곳이다.
4. **Task 오류가 세 곳에서 잘린다** [②].
   - 작업 표: `max-w-md truncate`, 마우스를 올려야 `title`로 보인다(`tasks/TasksPage.tsx:136`).
   - 작업·알림 센터: `line-clamp-2`(`tasks/NotificationCenter.tsx:226`).
   - 1024px 밑과 휴대폰: 오류 열이 `priority: 2`라서 **아예 사라진다**(`TasksPage.tsx:134`, `DataTable.tsx:60,436`).
   - Task 상세 화면은 없다. Task 행을 누르면 대상 목록(예: `/apply-sets`)으로만 간다.
5. **서버가 Task 오류를 구조 없이 영어 문자열 하나로 준다** [②]. `TaskStatus { state, error: Option<String>, progress }`(`crates/orbivisor-types/src/task.rs:507`)가 전부다. 오류 코드, 원인, 해결, 시작·끝 시각, 단계, 로그가 없다. 그래서 웹은 "QMP command failed: GenericError: TLS credentials support requires…" 같은 QEMU 원문을 그대로 보인다.
6. **API 오류는 코드가 있는데, 웹이 서버 설명을 버린다** [②]. `errors.*` 번역 188개 가운데 101개에 `{{message}}`가 없다. 번역이 있는 코드는 서버의 구체 설명("무엇이 이미 있는지" 등)이 사라진다(`i18n/errors.ts:66-72`).
7. **Task 대상이 이름 대신 id 조각으로 보인다** [②③]. "d4f36040 적용", "백업 저장소 8934075b 가비지 수집", "볼륨 78495e0d 삭제" 같은 식이다. 저장소 이름(lab-store)은 이미 받은 목록에 있는데도 찾지 않는다. 지운 리소스는 이름을 남기지 않는다(`tasks/target.ts:41-100`).
8. **선언 묶음은 CLI를 아는 사람에게만 뜻이 통한다** [③]. 화면 설명 첫 문장이 "orbivisorctl apply가 마지막에 선언한 것을 기억하고 클러스터와 견줍니다"이고, 빈 상태는 "orbivisorctl apply --set 이름 -f 디렉터리가 만듭니다"다. 그림도, "왜 쓰는지"도 없다. 작업 목록의 "적용" 행은 묶음 상세가 아니라 묶음 목록으로 간다(`tasks/target.ts:92-94`).
9. **VM 만들기 폼이 화면 3~4장 길이다** [⑥].
   - 높이: 1440×900에서 2954px(3.3화면), 1280×720에서 2970px(4.1화면).
   - 11단계가 한 줄로 길게 이어지고, "만들기" 단추는 맨 아래에만 있다.
   - 처음 보는 사람에게는 고급 칸(최대 vCPU, 최대 메모리, CPU 플래그, 머신 타입, 균형 조정기)이 이름·메모리와 섞여 있다.
   - **디스크가 비어서 시작하고 OS 이미지를 고르는 칸이 없다.**
10. **빌더(끌어 놓기)도 그림이 없다** [⑥].
    - 왼쪽 부품 목록이 2378px로 길고, 그 위쪽을 CPU 모델 30여 개가 차지한다. 디스크·네트워크 부품은 1700px 아래에 있어서 스크롤하며 끌어야 한다.
    - "VM 그림"은 실제로는 글 상자 9개다.
    - 아무것도 하기 전부터 빨간 오류 "소문자·숫자·-로 1~63자…"가 뜬다.
    - "계산", "살피기", "바탕" 같은 낯선 낱말을 쓴다.
11. **폭에 따라 줄이 깨진다** [⑤].
    - 설정 탭 12개가 1024px에서 넘친다.
    - 백업 행의 단추 4개가 1440px에서도 표를 넘친다(가로 스크롤 72~277px).
    - 노드 표 14열은 1440px에서 가로 756px 스크롤된다.
    - 홈 "최근 작업" 위젯은 1024px에서 노드·상태·오류 열이 잘려 안 보인다.
    - 지도 범례의 마지막 낱말 "오프라인"이 혼자 둘째 줄로 내려간다.
    - "자세히." 꼬리표가 홀로 한 줄이다.
    - 휴대폰에서 탭·보기 전환의 낱말이 반쯤 잘린다("Ne", "Floating"), 이동 경로도 "Settin… › Gene…"처럼 잘린다.
12. **업로드 진행이 토스트 한 줄뿐이다** [사용자 요청].
    - XHR 한 번에 통째로 보내고, 진행은 5% 단위로만 갱신한다. 속도·남은 시간·이어 올리기가 없다(`storage/upload.ts:101-153, 246-258`).
    - 작업 센터에 업로드가 나오지 않고, 다 올린 뒤 변환 Task부터 나온다.

### 1.3 제안 — 연관관계로 묶은 2단 사이드바 (묶음 9개)

규칙:

- 사이드바 = **1단 묶음 제목(아이콘+이름) → 그 아래 펼친 2단 항목**이다. 펼침 상태는 사용자별로 기억한다.
- 좁은 화면(<1280)에서는 아이콘 레일 + 펼침 창(flyout)으로 바꾼다.
- 영역 탭과 보기 전환은 **없앤다**. 화면 안 탭은 "한 대상의 상세(VM·노드·풀)"에서만 쓴다.
- 목록|폴더 같은 같은 목록의 다른 모양은 목록 오른쪽 위 아이콘 토글로 남긴다.
- 사이드바 맨 위에 "찾기(⌘K)"를 둔다.

## 2. 화면별 진단 [①④⑤]

표기는 다음과 같다.

- **설명**: 설명이 필요한 칸과 그 칸에 넣을 예문
- **용어**: 쉬운 말 대안
- **잘림/줄**: 폭에 따라 잘리거나 줄이 바뀌는 곳
- **스크롤**: 화면을 많이 내려야 하는 곳
- **중복**: 같은 정보가 여러 번 나오는 곳
- **빈 상태**: 목록이 비었을 때의 안내

### 2.0 모든 화면에 공통 — 도움말 체계가 없다 [①]

- 칸 아래 한 줄 설명(`Field.hint`)만 있고, 그나마 60%에 없다. 오류가 나면 설명을 감춘다(`Field.tsx:43`).
- 화면 머리 설명은 PageHeader 아래 회색 문단 하나다. 길면 2~3줄이고(배치 규칙, HA 검사, 최적 배치), 전문어가 가득하다.
- 도움말을 띄울 부품은 popover를 쓰는 화면 1개, tooltip을 쓰는 화면 2개뿐이다. 문서 링크는 0개다(`docsHref` 0곳).
- **제안**(업계 §5):
  - 칸마다 "항상 보이는 한 줄"을 둔다.
  - 칸 이름 옆 ⓘ를 누르면 **오른쪽 도움말 패널**이 열린다. 패널에는 "무엇인가 / 언제 바꾸나 / 기본값·권장값 / 작은 그림"과 문서 링크 하나를 둔다.
  - 화면마다 머리에 "이 화면은?" ⓘ를 하나 둔다.
  - 오류가 나도 설명은 그대로 두고, 오류를 그 아래에 더한다.

  - QEMU 원문이다. 원인(마이그레이션 TLS 인증서 없음 또는 QEMU 빌드)과 해결이 없다.
  - 대상 VM은 지금 없어서 id로 보인다.

### 3.2 서버가 주는 것 / 웹이 버리는 것

| 정보 | 서버 | 웹 |
|---|---|---|
| 무엇을(op 종류·대상 id·실행 노드) | `TaskSpec{op,target,node}` | 씀. 대상 이름을 못 찾으면 id 8자(`target.ts`) |
| 누가 요청 | 레이블 `REQUESTED_BY`(사용자 id, `crates/orbivisor-api/src/tasks.rs:936`) | **버림**(어디에도 안 보임) |
| 언제 | UUIDv7 id 안의 만든 시각뿐 | 만든 시각만. 시작·끝·걸린 시간이 **없음**(서버에도 없음) |
| 상태 | pending/running/succeeded/failed | 씀 |
| 진행 | `progress{stage, done, total}`(마이그레이션·디스크 복사 일부) | 씀 |
| 오류 | `error: Option<String>`. 영어, 원문, 체인(`{e:#}`) | 그대로(잘라서) |
| 오류 코드·원인·해결 | **없음** | — |
| 단계·로그 | **없음**(apply만 "step i/n" 문자열 속에) | — |
| 성공 + 경고 | `succeeded` + `error`(경고 문장) | 토스트 경고만, 표에서는 "오류" 열에 섞임 |
| API 오류 | `{code, message, details}`, 고유 code 약 56종 | 188개 번역. 101개는 `message`를 버림 |

### 3.3 "실패 원인·해결"을 보이려면 서버에 필요한 것

1. **`TaskStatus`에 구조 오류**를 더한다. 옛 노드 호환을 위해 `error` 문자열은 남긴다.
   ```rust
   pub struct TaskFailure {
       pub code: String,            // "migration_tls_missing", "apply_invalid_spec", "storage_full" …
       pub message: String,         // 지금 error (원문, 영어)
       pub params: Map<String,Value>,// {"vm":"web","node":"svc02","need_gib":20,"free_gib":3}
       pub step: Option<String>,    // "copying-disks" / "step 1/1 create AlertRule p73-live-check"
       pub retryable: bool,
       pub cause: Option<String>,   // 하위 원인 코드(예: "qmp_generic_error")
   }
   ```
   웹은 `taskErrors.<code>.{title,cause,fix}` 번역 + `params`로 "무엇이 / 왜 / 어떻게"를 만든다. 원문은 "자세한 원문 ▸" 접기에 둔다. 우선 Task 실패 상위 20개 경로에 code를 단다. 대상은 `orbivisor-api/src` 안의 `Err(format!)` 260곳이고, 빈도순으로 고른다(Task 기록에서 집계).
2. **시각**: `started_at`, `finished_at`(unix ms). 걸린 시간을 보이고 "멈춘 것 같음"을 판정하는 데 쓴다.
3. **요청자 이름**: 레이블 id를 이름으로 내보내는 `requested_by` 칸.
4. **대상 이름 스냅숏**: Task를 만들 때 `target_name`(+ kind)을 적어 둔다. 지운 VM·볼륨·계획도 이름이 남는다. apply는 `set` 이름 또는 "파일 N개 적용".
5. **단계·이벤트 로그**: Task마다 최근 이벤트 50개 링(`{ts, level, msg}`)이다. 마이그레이션·백업·apply·업로드 변환에 쓴다. `/tasks/{id}/events`나 `TaskStatus.events`.
6. **경보 런북**: `AlertRule`에 `runbook`(설명·해결 문장, 기본 규칙은 내장 번역 키)을 둔다. Nutanix식 영향·원인·해결이다.
7. **API 오류**: 웹 `codeMessage`에서 번역 뒤에 서버 `message`를 "자세히"로 붙인다. 번역에 `{{message}}`가 없어도 버리지 않는다.
