# Orbivisor 계획 68: 백업 저장소 2 — 중복 제거 청크 저장소, 검증, 클라이언트 쪽 암호화, S3 호환 저장소, 라이브 복원 구현 계획

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** 계획 27·28·40·41의 백업(디스크마다 압축 qcow2, dirty bitmap 증분 체인, 원격 클러스터로 파일 복제)을 Proxmox Backup Server·Veeam과 견줄 저장 방식과 운영으로 넓힌다: 고정 4 MiB **중복 제거 청크 저장소**(백업마다 완전한 인덱스 — 체인 없음, 아무 백업이나 지움), 청크·매니페스트를 다시 읽는 **검증 작업**(깨진 청크는 옆으로, 다음 백업이 고침, 경보), 노드에서 하는 **AES-256-GCM 암호화**(키가 든 청크 id·결정적 nonce로 dedup 유지, 복구 키·저장소 안 escrow), **S3 호환 객체 저장소** 백엔드(직접 짠 SigV4 클라이언트)와 저장소 사이 복사(계층)·읽기 전용 붙이기(DR), 디스크를 다 받기 전에 VM을 켜는 **라이브 복원**(오버레이 + NBD + `blockdev-mirror` 갈아타기). GC·보존, 옛 백업 그대로 두기와 옮기기, 원격 복제의 없는 청크만 보내기도 넣는다.

**Architecture:**
- **새 루트 리소스 `BackupStore`**(백엔드: 백업 풀 안 `{루트}/store/{id}/` 또는 S3, 암호화 키는 Raft에만 — API·watch·감사에서 뺌, GC·검증 일정, 읽기 전용). `Backup`은 `pool` 또는 `store` 하나. 데이터(청크·인덱스·매니페스트 v3·블롭)는 저장소 안에만, Raft에는 리소스와 저장소 상태만.
- **읽기는 pull**: 실행 중 VM은 디스크마다 fleece qcow2(backing = 살아 있는 디스크) + `blockdev-backup sync=none`을 한 `transaction`으로(비트맵 얼리기·새 비트맵 포함), 유닉스 소켓 NBD로 읽기 전용 내보내기(증분은 `qemu:dirty-bitmap` 문맥). 꺼진 VM은 `qemu-nbd`. opld의 Task가 청크로 나눠 해시·압축(lz4)·암호화해 올린다. 저장소 쪽 스냅샷이 필요 없어 블록 풀도 멈추지 않고 공유 LVM도 실행 중에 백업된다.
- **복원 쪽은 헬퍼 하나** `orbivisord backup-serve`(표준 입력 설정, `opl-bkserve-<id>.scope`): 백업 디스크를 읽기 전용 NBD로. 보통 복원은 지금의 `import_volume`이 NBD 원본을 받아 `qemu-img convert`, 라이브 복원은 QEMU가 오버레이의 backing으로 읽는다.
- **GC는 표시·쓸기**: 저장소 시계의 기준 시각 T0, GC 시작 때 진행 중이던 백업을 기다림, Raft 쓰기 잠금(`committing` ↔ `sweeping`)과 늦은 표시, 쓸기 뒤 커밋은 건너뛴 청크를 다시 확인. 표시 집합은 Bloom 필터(오탐은 쓰레기를 남길 뿐).
- **라이브 복원은 이어 가는 Task**: VM의 디스크 i는 `disk{i}-lrsrc`(NBD, `reconnect-delay`) → `disk{i}-lr`(로컬 오버레이) 위에서 켜지고, mirror(`write-blocking`)가 대상 노드 `disk{i}`로 옮긴 뒤 `job-complete`로 갈아탄다 — 그 뒤 노드 이름까지 보통 VM과 같다. 헬퍼·opld·QEMU가 죽어도 이어 간다. 끝날 때까지 HA·마이그레이션·스냅샷·백업은 409 `vm_restoring`.
- **이 기능을 쓰지 않는 클러스터와 옛 백업은 바이트까지 지금과 같다**(Raft JSON, qcow2·매니페스트 v1·v2, 복제 프로토콜, VM 명령줄). 기능 하나 **`backup-store`**가 새 칸·리소스·Task를 가린다(섞인 클러스터는 409 `cluster_upgrading`). 데이터는 조용히 지우지 않는다.

**Tech Stack:** Rust(opl-types·opl-cluster·새 opl-store·opl-qemu·opl-driver·opl-reconciler·opl-api·oplctl·opld), QEMU 8.2·10.0·Homebrew(QMP `blockdev-backup`·`block-export-add`·`blockdev-mirror`·비트맵), `qemu-nbd`(qemu-utils), NBD 프로토콜(순수 Rust 클라이언트·서버), ring(SHA-256·HMAC·HKDF·AES-256-GCM), argon2, lz4_flex(새 의존성, 순수 Rust), hyper 1·tokio-rustls·rustls-native-certs·roxmltree(S3, SigV4 직접), axum(가짜 S3), SeaweedFS(CI 컨테이너 — S3 호환, MinIO는 2025년 가을부터 배포 끝남), React 19·TanStack Query.

## 설계 결정

- **청크는 CDC·64 KiB 대신 고정 4 MiB:** 블록 장치는 바이트가 밀리지 않고, 고정 청크가 비트맵·임의 읽기(라이브 복원·계획 69)와 곧바로 맞는다(PBS VM 이미지와 같음). 백업마다 완전한 인덱스(1 TiB에 8 MiB)라 체인이 없다.
- **QEMU에서 꺼내기는 로컬 임시 qcow2 밀기·저장소 스냅샷·QEMU 덧대기 대신 fleecing + 유닉스 NBD pull:** 덮어쓴 옛 블록만 담고 모든 풀에서 같으며 VM을 멈추지 않는다. fleece가 차면 게스트 쓰기가 실패하는 QEMU 동작은 미리 확인 + 1초 지킴이로 막는다.
- **압축은 zstd(C) 대신 lz4_flex(순수 Rust), 해시는 BLAKE3 대신 ring SHA-256:** 순수 Rust 트리를 지키고, 이미 있는 CPU 가속을 쓴다. 헤더에 압축 종류가 있어 나중에 더할 수 있다.
- **암호화는 무작위 nonce 대신 결정적 nonce(청크 id의 PRF):** 키마다 청크 수 한계가 없고 같은 청크는 같은 바이트(동시 쓰기 안전), 새는 것은 이미 id로 드러난 "같다"뿐. 청크 id는 평문 해시 대신 HMAC.
- **키는 KMS·노드 파일 대신 Raft + 복구 키 + 저장소 안 escrow:** 위협 모델이 저장소 쪽이고 Raft는 이미 비밀(원격 토큰)을 두는 곳. 클러스터를 잃어도 복구 키나 암호 문구로 연다.
- **GC는 atime·참조 계수·전체 잠금 대신 표시·쓸기 + Raft 쓰기 잠금 + 늦은 표시:** S3에 atime이 없고, 짧은 커밋 구간과 쓸기만 서로 막는다. 안전은 모형 proptest로 지킨다.
- **S3 클라이언트는 aws-sdk·object_store·reqwest(OpenSSL) 대신 hyper + rustls + 직접 SigV4:** 연산 여섯뿐이고 AWS 공개 벡터로 확인한다.
- **라이브 복원은 `block-stream`·`alloc-track` 대신 오버레이 + NBD + mirror 갈아타기:** 모든 풀에서 같고 대상 볼륨이 끝날 때까지 장치에 붙지 않는다. 대가는 노드에 묶인 오버레이(HA 없음).
- **저장소는 풀 표시 넓히기 대신 새 리소스:** S3는 풀이 아니고 키·일정·GC 상태·주인 표식이 풀 코드에 들어가지 않게.

## 알고 받아들인 제한

- **fleece:** 지킴이가 1초마다 보므로 1초에 1 GiB보다 빨리 쓰는 게스트는 앞지를 수 있다. 그때 QEMU는 **게스트 쓰기를 실패시키지 않고**(`on-cbw-error: break-snapshot`) 시점 내보내기의 읽기만 실패한다 — 그 백업만 실패한다(스테이지 3 탐침: 160 MiB APFS 이미지에 플리싱, 200 MiB 덮어쓰기). 플리싱은 VM 상태 디렉터리에 두므로 그 파일시스템을 넉넉히.
- **라이브 복원:** 오버레이가 노드 로컬이라 끝날 때까지 HA가 없고, 노드를 영영 잃으면 라이브 복원 뒤 게스트가 쓴 것을 잃는다. 첫 읽기는 4 MiB 청크 단위와 S3 지연만큼 느리다 — 이 Mac 로컬 저장소에서 배선으로 켠 QEMU가 뜨기까지 약 65 ms(게스트 OS 없음), S3의 처리량·첫 부팅은 GitHub `backup-s3`의 `PROBE` 줄(아래 GitHub 탐침)로 채운다. 실제 게스트 OS의 첫 부팅 시간은 재지 않았다.
- **꺼진 VM:** 늘 디스크 전체를 읽는다(공간·전송은 새 청크만).
- **할당량 `backup_bytes`:** "그 백업이 처음 쓴 바이트"라 dedup된 고유 공간과 다르고, 진행 중 백업 하나는 한도를 넘길 수 있다.
- **S3:** 강한 일관성 구현만, 실제 AWS·Wasabi·Ceph RGW는 CI가 아닌 손 확인(가이드 절차). CI는 MinIO가 배포를 끝내 **SeaweedFS 4.50**으로 바꿨다. 지우기는 하나씩(`DeleteObjects` 없음), multipart 없음(받는 본문 1 GiB — 128 TiB 디스크의 인덱스까지).
- **검증:** 옛 풀 백업은 검증하지 않는다(`backup verify`가 400 — `convert`로 옮겨 검증). 깨진 청크를 다른 사본에서 자동으로 고치지 않는다.
- **블록 풀·공유 LVM 위 실행 중 저장소 백업**은 실제 저장소로 시험하지 않았다(fleecing은 풀 종류와 무관한 QEMU 블록 층 — dir qcow2와 가짜 하이퍼바이저로 봄).
- **실제 QEMU의 라이브 복원 죽이기 시험**(헬퍼 `kill -9`·opld 다시 시작·QEMU `kill -9`)은 64 MiB 디스크가 1초 안에 다 옮겨져 이 Mac에서 결정적으로 짤 수 없어, 같은 Task 길의 가짜 하이퍼바이저 시험·드라이버 재연결 탐침과 `backup-s3`의 512 MiB 디스크 시험으로 나눴다. QEMU `kill -9` 도중은 가짜 하이퍼바이저로만.
- **웹:** 마법사는 만들기 전 연결 확인이 없다(만든 뒤 서랍), S3 끝점은 `https://`만, 라이브 복원 노드는 고르지 못한다. `backup-job list`의 `POOL` 칸은 저장소 작업이면 `-`.
