# Orbivisor 계획 65: SDN(OVN) 1 — OVN 설치·구성, 리더 OvnSync, 논리 스위치·서브넷·IPAM·DHCP, 포트 바인딩 구현 계획

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** 관리자가 만든 Linux 브리지·VLAN, 정적 VXLAN, nftables 보안 그룹뿐이고 VM이 가질 IP를 Orbivisor가 모르던 네트워크를 넓혀, **OVN을 뒷단으로** 한 SDN 네트워크(Geneve 위의 논리 스위치)를 더한다. Orbivisor가 OVN을 **설치하고 세우며**(중앙 1·3·5, 노드마다 chassis), 네트워크 안 **서브넷**과 **Raft IPAM**이 VM NIC 주소를 정하고 **OVN 내장 DHCPv4**가 그 주소를 주며, **포트 보안**이 위조를 막고, VM 켜기·라이브 마이그레이션·HA가 OVN 포트 바인딩을 따라간다. 라우터·외부 연결·보안 그룹의 OVN 이전은 계획 66, 부하 분산·QoS·옮기기 도구는 계획 67이다.

**Architecture:**
- **원하는 상태는 Raft에만 있다.** API는 Raft만 쓰고 OVN을 부르지 않는다. 리더 루프 `OvnSync`가 Raft의 SDN 네트워크·서브넷·VM NIC를 순수 함수 `desired`로 NB 행(`Logical_Switch`·`Logical_Switch_Port`·`DHCP_Options`)으로 그려 주인 표시가 있는 NB 행과 견주고 다른 것만 쓴다. NB는 다시 만들 수 있는 파생물이다.
- **펜싱 토큰.** 트랜잭션마다 `NB_Global.external_ids`의 `wait` + 토큰 `"<Raft 임기>:<인덱스>"` `update`. 더 큰 임기를 본 옛 리더는 쓰지 않는다.
- **OVSDB JSON-RPC를 직접**(`tokio-rustls`, 새 크레이트 없음): 클러스터 CA mTLS, 서버 이름 확인, 쓰는 쪽은 클러스터 리더에만, `echo` 답하기. `ovn-nbctl`을 부르지 않는다.
- **OVN 제어 평면은 Orbivisor가 세운다**(계획 56 Ceph와 같은 길): `sdn-*` Task가 빠진 꾸러미만 apt로 깔고, 배포판 중앙 단위를 끄고 가린 뒤 Orbivisor 단위(`opl-ovn-nb`·`-sb`·`-northd`, 노드 주소의 `pssl`만, DB는 `/var/lib/opl/ovn`)를 띄운다. 중앙은 관리자가 고른 고정 집합이고 투표 멤버를 따라가지 않는다. 노드마다 `SdnAgent`가 chassis·단위·스키마 변환·오래된 포트를 맞춘다.
- **IPAM은 VM 스펙의 칸**(`NicSpec.ips`)이고 겹침은 Raft 상태 머신의 배타 값 `("ip", "<네트워크>/<주소>")`이 막는다(MAC과 같은 길). 있던 NIC는 저절로 채우지 않는다.
- **이 기능을 쓰지 않는 클러스터는 바이트까지 지금과 같다**(Raft JSON, 명령줄, tap 명령, cloud-init 씨앗). **기능 하나** `sdn`이 모든 새 칸·리소스·Task를 가리고(섞인 클러스터는 409 `cluster_upgrading`), `sdn init` 전에는 꾸러미를 찾지도 않는다.

**Tech Stack:** Rust(opl-types·opl-cluster·opl-qemu·opl-driver·opl-reconciler·opl-api·oplctl·opld), OVN 24.03·Open vSwitch 3.3(Ubuntu 24.04 꾸러미), OVSDB JSON-RPC(RFC 7047), `tokio-rustls`, systemd, React 19·TanStack Query, Vitest·msw, Playwright(opld `web-it`). 새 의존성 없음.

**설계 문서:** `docs/superpowers/specs/2026-11-20-sdn-ovn-design.md`

## 설계 결정

- **NB 쓰기는 API 요청마다(Neutron) 대신 Raft에서 리더가 수준 맞추기:** 원하는 상태가 이미 Raft에 있고 리더 루프가 있으므로 API가 OVN에 매이지 않고 리더가 바뀌어도 같은 함수가 같은 답을 낸다. 대가는 최종 일관성(보통 1초 안)이라 켜기는 바인딩을 기다리지 않고 마이그레이션 받기만 기다린다.
- **NB 클라이언트는 `ovn-nbctl` 대신 JSON-RPC 직접:** 리더가 macOS일 수 있고, "다른 것만 한 트랜잭션에 + 펜싱 `wait`"을 명령줄로 만들기 어렵다. 프로토콜이 작고 TLS 크레이트가 이미 있다.
- **IPAM은 OVN 자체(`dynamic`) 대신 Raft:** OVN IPAM은 IPv4 하나·NB에만 기록이라 NB를 다시 만들면 주소가 바뀔 수 있다. Raft에 두면 MAC과 같은 겹침 검사로 끝나고 cloud-init·API가 주소를 안다.
- **포트는 새 리소스 대신 NIC 스펙의 칸, 서브넷은 네트워크 스펙 안(Proxmox VNet › 서브넷):** 한 리비전으로 바뀌고 지우기 검사가 하나다.
- **중앙은 투표 멤버를 따라가지 않는 고정 집합:** OVN Raft 멤버십 바꾸기는 DB 복사·따라잡기가 드는 느린 일이라 `VoterKeeper`의 1초 승격·강등을 따라가면 NB 정족수를 잃을 수 있다.
- **중앙 실행은 배포판 `ovn-ctl` 대신 Orbivisor 단위:** 듣는 주소를 노드 주소 하나로, DB를 Orbivisor 자리로. 대가로 스키마 변환을 에이전트가 한다.
- **오버레이는 Geneve:** OVN 기본이고 지금 VXLAN(4789)과 포트가 달라 함께 돈다.
- **65는 SDN NIC에 보안 그룹을 받지 않음:** OVS 포트는 nftables bridge 훅을 타지 않고, OVS 앞에 브리지를 하나 더 두면 66에서 버릴 장치가 된다. 65 네트워크는 라우터가 없어 고립돼 있다.

## 완료 기준 (계획 65)

- 옛 JSON(`NetworkSpec`·`NicSpec`·`NodeStatus`·`RuntimeNic`)이 바이트 그대로이고, SDN을 쓰지 않는 클러스터의 Raft·명령줄·tap 명령·cloud-init 씨앗과 instance-id가 계획 64와 같다. 업그레이드 중(`sdn`을 모르는 노드가 있음) 새 쓰기는 409 `cluster_upgrading`이고 노드는 `status.sdn`을 쓰지 않는다. `sdn init` 전에는 꾸러미를 찾지도 않는다.
- 깨끗한 Ubuntu 24.04에서 `sdn init`이 OVN을 실제로 설치하고 배포판 단위를 끄며, NB·SB가 노드 주소의 `pssl`에만 듣고 클러스터 CA 인증서로만 붙는다(다른 CA·인증서 없음·평문 거절). SB `Chassis` 이름이 노드 UUID, encap이 Geneve·underlay다. 다시 하면 잇고, 두 번째 ovsdb 서버가 합류·떠나기를 하며, 마지막 중앙은 뺄 수 없다.
- OvnSync가 다른 것만 쓰고(다시 부르면 트랜잭션 없음), 남의 행·태그 없는 행을 두며, 지운 우리 행을 되살리고, 더 큰 임기의 토큰을 보면 쓰지 않으며, 2000개를 넘으면 네트워크마다 나누고, Raft 읽기 실패에 지우지 않는다. 포트 5천 전체 다시 맞추기가 목표 2초 안이다.
- 두 쓰기가 같은 주소를 노리면 하나만 되고(Raft), 다른 네트워크의 같은 주소는 된다. 복제·배포·가져오기·복원·되돌리기의 주소 규칙, 켜진 VM 주소 바꾸기 409, `subnet_in_use`, `ip_exhausted`가 맞다.
- 실제 OVN에서 이름공간 포트 둘이 busybox `udhcpc`로 IPAM 주소·접두사·MTU 1442·DNS를 받고 서로 ping하며 위조 주소는 막힌다. SDN NIC의 QEMU VM tap이 `br-int`에 붙어 이 chassis에 바인딩되고(`ovn-installed`, LSP `up`), 실제 Ubuntu 게스트가 OVN DHCP로 IPAM 주소를 받는다.

## 알고 받아들인 제한

- **실제로 보지 못한 것:** chassis 둘 사이의 Geneve, 라이브 마이그레이션의 두 chassis 바인딩, 중앙 셋의 실제 노드 장애. GitHub 러너 하나는 OVS·`system-id`가 하나라 opld를 둘 띄워도 chassis가 하나다. 받는 쪽 기다림·거절은 드라이버 시험, 쉼표 `requested-chassis`·`rarp`는 OvnSync 시험, 중앙 합류·떠나기는 같은 러너 127.0.0.2의 ovsdb 한 쌍으로만 본다.
- **죽은 중앙 노드는 뺄 수 없다:** 빼기 Task가 그 노드에서 돌아야 해 오프라인 중앙은 409다. `ovs-appctl cluster/kick` 뒤 Raft를 고치는 길이나 `--force`는 없다.
- **"10초 안에 포트가 바인딩되지 않음"은 opld 로그뿐:** 드라이버에서 VM 이벤트로 나를 길이 없어 API·웹에 보이지 않는다.
- **있던 NIC 채우기(`--fill`)는 CLI만:** 웹·API에는 없고 CLI가 VM 스펙에 주소를 적어 `PUT`한다. `PUT`으로 주소를 비울 수 없다(주소 없는 있던 NIC는 지금 주소를 둔다).
- **SB RBAC 없음:** chassis가 다른 chassis의 SB 행도 쓸 수 있다(계획 67). OVS 서버는 상대 인증서의 CA만 보고 이름은 보지 않는다.
- 서브넷은 체계마다 하나, IPv6는 DHCP 없이 cloud-init 고정 주소(게이트웨이 없음). DHCP는 `router`를 주지 않는다. 서브넷 DHCP·DNS만 바꾸면 instance-id가 그대로라 고정 주소 게스트는 다시 적용하지 않는다.
- 템플릿 배포 `--count` 2 이상에는 주소를 고를 수 없다. 원격 복제를 받는 클러스터에는 같은 이름의 SDN 네트워크가 있어야 하고 주소가 겹치면 받기가 실패한다.
- 중앙의 OVN 판은 Raft `release`와 주·부 판이 같아야 한다(꾸러미를 올릴 때 모든 중앙을 함께). 새로 합류한 노드에는 chassis를 저절로 깔지 않는다.
- `opld` 디버그 빌드의 시험 두 개가 스택이 빠듯했다(`replica_receive::sweep_deletes_replicas_no_longer_wanted`, `member::tests::a_restart_with_new_links_signs_the_node_cert_again` — `Box::pin`과 8 MiB 스레드로 고침, `RUST_MIN_STACK=3MB`로 겨우 통과).
