# Orbivisor 계획 64: NUMA 토폴로지·vNUMA·전용 CPU 고정·hugepages 구현 계획

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** 게스트가 `-smp`와 `-m`뿐이고 vCPU·메모리가 호스트 어디에든 놓이던 것을 넓혀, 노드가 **NUMA 토폴로지**를 알리고, VM이 **게스트 NUMA 노드(vNUMA)**·**전용 CPU 정책(pCPU 독점 고정)과 스레드·에뮬레이터 정책**·**hugepages(2M·1G)**·**호스트 노드 메모리 묶기**를 쓰며, 전용 pCPU·hugepages를 **노드 자원으로 세어** 동시 배치·마이그레이션·HA가 같은 자원을 두 번 잡지 않게 한다.

**Architecture:**
- **호스트에 매인 결정은 켜는 노드가 정하고 기록한다.** 어느 pCPU·어느 호스트 노드는 QEMU가 도는 노드가 켤 때 골라 `RunningHardware.host_placement`에, 게스트가 보는 모양(노드·거리·페이지·정책)은 `RunningHardware.numa`에 남긴다(계획 63 `cpu_resolved`와 같은 길). 라이브 마이그레이션은 모양을 기록 그대로 두고 대상이 pCPU만 다시 고른다. HA 복구는 다시 켜기라 스펙에서 새로 정한다.
- **세 층의 자원 세기.** 같은 순수 함수(`opl_types::numa` — `layout`·`fit`·`fit_fixed`·`demand`·`exceeded`)를 Raft 받아들이기 검사(합계, 커밋 순서로 경쟁을 막음), API 스케줄러(노드마다 맞춤 어림), 노드 할당기(잠금 안에서 정확한 pCPU·페이지, `/sys`의 실제 빈 hugepages)가 쓴다.
- **노드 CPU 세 집합**(OpenStack `cpu_dedicated_set`·`cpu_shared_set`): 예약·전용은 노드 설정 `host_resources`, 공유는 나머지. 설정이 없으면 지금과 같다.
- **Orbivisor는 커널 명령줄을 고치지 않는다.** `isolcpus`·1G hugepages는 가이드와 경고로, 실행 중 hugepages 예약만 노드 설정으로 한다. hugepages는 memfd hugetlb(마운트 없음)와 prealloc.
- **고정은 `sched_setaffinity` + 스코프 `AllowedCPUs`**(cgroup v2 cpuset). 검사 루프가 30초마다 어긋남을 고친다.
- **이 기능을 쓰지 않는 VM·노드는 바이트까지 지금과 같다**(스펙·기록 JSON, 명령줄, `systemd-run` 인자). **기능 하나** `numa`가 모든 새 칸·노드 쓰기·할당량 차원·RPC를 가린다(섞인 클러스터는 409 `cluster_upgrading`).

**Tech Stack:** Rust(opl-types·opl-cluster·opl-qemu·opl-driver·opl-reconciler·opl-peer·opl-api·oplctl·opld), Linux `/sys`·`sched_setaffinity`·systemd 스코프, QEMU `-numa`·`memory-backend-memfd`, React 19·TanStack Query, Vitest·msw, Playwright(opld `web-it`). 새 의존성 없음.

**설계 문서:** `docs/superpowers/specs/2026-11-19-numa-pinning-design.md`
**선행 계획:** 계획 1~63 (완료)

## 설계 결정

- **VM마다 아무 pCPU 대신 정적 세 집합(OpenStack과 같음):** 공유 VM이 전용 pCPU를 피하는 규칙이 공유 집합 하나로 단순하고, 전용 VM이 켜질 때 공유 VM을 다시 묶지 않는다.
- **cgroup 하위 그룹마다 vCPU(libvirt) 대신 `sched_setaffinity` + 스코프 `AllowedCPUs`:** 스코프는 VM마다 이미 있고, root가 친화를 넓힐 수 있어 상한은 cpuset이 쥔다.
- **호스트 격리는 보고만:** VM 스코프가 `system.slice` 안이라 그것을 묶으면 VM도 묶인다. `CPUAffinity=`·`isolcpus`가 표준 길이고 Orbivisor는 어긋남을 경고한다.
- **hugepages는 켤 때 할당 대신 정적 풀(+ 선택적 실행 중 예약):** 1G를 켤 때 할당하면 조각으로 실패하기 쉽고, 풀이어야 스케줄러가 센다. 백엔드는 hugetlbfs 대신 memfd(마운트·파일 정리 없음).
- **자원 세기는 Raft 합계 + 노드 할당기:** API 잠금은 노드 하나 안이고, peer RPC는 HA 경로를 다른 노드 응답에 맨다. 정확한 pCPU는 그 노드가, 합계만 Raft가.
- **vNUMA `auto`는 소켓의 약수:** 노드를 소켓 단위로 두어야 게스트 토폴로지가 어긋나지 않는다. 소켓 하나인 VM은 나누지 않는다(웹 폼에 소켓 칸을 더함).
- **전용 + 핫플러그는 상한까지 잡기:** 실행 중 pCPU를 새로 구하다 실패하는 일이 없다.
- **균형 조정기는 전용 VM을 건너뜀:** 자기 pCPU에서 돌아 옮겨 얻는 것이 없다.

## 완료 기준 (계획 64)

- 옛 JSON(`VmSpec`·`CpuSpec`·`NodeSpec`·`NodeStatus`·`RunningHardware`)이 바이트 그대로이고, 이 기능을 쓰지 않는 VM의 명령줄·`systemd-run` 인자·기록이 계획 63과 같다. 업그레이드 중(`numa`를 모르는 노드가 있음) 노드는 토폴로지를 쓰지 않고 새 쓰기는 409 `cluster_upgrading`이다.
- `layout`·`fit`·`fit_fixed`·`demand`·`exceeded`·`pinning` 표 시험이 통과한다: 노드 하나·둘·넷, 스레드 정책 셋 × SMT 있음·없음, 에뮬레이터 `isolate`, 2M·1G·`any`, 조각난 노드, 거리 순서, L3 고르기, 메모리 나눔과 단위.
- 탐침 고정물 넷의 내용·경고가 맞고 256 CPU 토폴로지가 4 KB 안이며, 실제 Linux 탐침이 GitHub 러너와 svc01에서 된다.
- 두 팔로워가 같은 노드의 마지막 전용 CPU에 동시에 VM을 만들고 켜도 하나만 된다(Raft). 스케줄러가 NUMA로 거르고 노드마다 까닭을 주며, 마이그레이션은 대상이 둘 수 없으면 409 `migration_unsupported`, 균형 조정기는 전용 VM을 건너뛴다.
- 실제 KVM에서 전용 VM의 vCPU 스레드가 전용 CPU 하나씩, 나머지 스레드가 공유 CPU에 있고 스코프 cpuset이 맞으며, 2M hugepages VM이 `HugePages_Free`를 그만큼 줄이고, 동시에 켠 전용 VM 둘 가운데 하나가 409이며, 실행 중 붙인 vCPU가 잡아 둔 pCPU에, 두 opld 사이 마이그레이션 뒤 받는 쪽 스레드가 대상의 전용 CPU에 고정된다.
- 실제 Ubuntu 게스트가 `--sockets 2 --numa 2`로 NUMA 노드 둘(소켓마다 CPU, 메모리 반씩)을 본다.
- API: 검증 400, 권한 행렬(`vm.dedicated`, operator 403, `/topology/*` 루트 `cluster.read`), 할당량 `dedicated_vcpus` 409, `host_resources` 검증·409·`force`·칸이 없으면 그대로, 복제·배포 덮어쓰기가 맞다.
- 웹: VM 폼의 배치 칸(소켓·정책·노드 수·권한 막기), 요약 카드와 고정 표, 노드 토폴로지 격자와 호스트 자원 대화상자(409·"그래도 저장"), 마이그레이션 대화상자의 막힌 노드가 vitest로, VM 폼 NUMA 저장과 노드 "NUMA 토폴로지"가 브라우저 E2E로 보인다.
- `cargo fmt`·`clippy -D warnings`·`cargo test --workspace`, `pnpm typecheck`·`lint`·`test`, 로컬 브라우저 E2E가 통과하고 svc01 일반 시험과 GitHub `linux-kvm`·`install-media`가 통과한다.

## 알고 받아들인 제한

- **실제로 보지 못한 것:** 게스트 노드 둘 이상의 virtio-mem(실행 중 노드마다 크기 바꾸기 `set_memory`)은 명령줄·Mock 시험만이고 실제 KVM으로 돌리지 않았다. 공유 vNUMA의 QMP `node-id` 확인도 GitHub `linux-kvm`에서는 하지 않았다(실제 게스트 `install-media`가 게스트 쪽에서 본다). 호스트 노드 둘 이상의 맞춤·거리·묶기, 1G hugepages, SMT 스레드 정책은 고정물·Mock으로만 본다(시험 장비가 모두 NUMA 노드 하나·SMT 없음).
- **swtpm은 다시 고정하지 않는다:** 켤 때의 에뮬레이터 집합에 남고, 공유 집합이 바뀌어도 검사 루프의 `repin`은 QEMU만 다시 건다.
- **`force`로 줄인 전용 집합:** 밖으로 나간 pCPU의 전용 VM에 보류 `numa`를 만들지 않는다(보류는 스펙과 기록의 차이라 노드 설정에서 만들 길이 없음). 응답 경고에 적고, VM은 기록된 pCPU에 남았다가 다음 전원 껐다 켜기 때 새로 고른다.
- **웹 노드 격자에 소켓 층이 없다:** 토폴로지가 CPU마다 소켓 번호를 갖지 않아 호스트 노드 › L3 › 코어 › 스레드로 그린다.
- 웹의 "들어갈 노드"는 노드마다 남은 수만 보는 어림이다(호스트 노드 나눔·`isolate` 형제는 켤 때 서버가 본다). 노드마다 직접 나누는 표는 VM 폼에만 있고 복제·배포·가져오기는 노드 수까지다.
- 핫플러그 VM은 켤 때 vCPU가 소켓 0부터 채워져 앞 게스트 노드에 몰린다. 전용 VM은 핫플러그 상한까지 pCPU를 잡는다(빈 자리도).
- hugepages 실행 중 예약이 모자라면 다시 시도하지 않고 경고만 한다(설정을 바꾸거나 opld를 다시 시작). 설정에서 뺀 예약은 커널 수를 그대로 둔다.
- 커널 일꾼 스레드(`kvm-nx-lpage-recovery`·`vhost-*`)는 친화를 걸지 않는다(커널이 정함, 상한은 스코프 cpuset).
- HA 용량 예약(`ha_capacity`)은 메모리만 보고 전용 CPU를 세지 않는다. 비우기·균형 조정에서 전용 VM의 노드 안 조각 모음은 없다.
- GitHub 러너의 x86 노드 하나 탐침 고정물은 아직 저장소에 없다(`numa-it` `probes_this_host`가 러너 JSON을 로그에 찍는다).
- aarch64 64K 커널의 512M hugepages 풀은 세지 않는다(2M·1G만).
